8-01 GPU 是谁：训练 vs 推理、显存 vs 内存

这一关不敲命令，只把三组词分清。它们是后面所有关卡的"地图"。

一、训练 vs 推理（最重要的区分）

阶段在干什么资源特点你以后会怎么碰到
训练拿海量数据反复调整模型参数几天到几个月、几百张卡、满负荷运转训练任务挂了/变慢了；要重启、要从断点续训
推理拿训好的模型回答用户长期在线、显存吃紧、要低延迟推理服务起不来、变慢、显存不够、被限流

一句话记忆：训练烧算力，推理吃显存；训练是"批处理"，推理是"在线服务"。AI 运维的日常里，推理占大头（因为它在线上跑，随时随地会出问题）。

二、显存 vs 内存（两个不同的"内存"）

内存（RAM）  ← 主机/服务器的内存，给 CPU 用；用 ps / free 看
显存（VRAM） ← 显卡自己的内存，给 GPU 用；用 nvidia-smi 看

解读：模型参数、中间结果都放在显存里。显存不够，程序直接报错（8-04 的 OOM）。主机内存再大也帮不上显存——这是新手最容易混的一点。

三、为什么 GPU 比 CPU 快（实战里常被问到）

CPU 像"几个博士"：单个算得很快，但人手少。GPU 像"几千个小学生"：单个算得慢，但人多、能同时干同一件简单的事。矩阵运算是"同样的简单计算重复几百万次"，正好是 GPU 的主场 —— 这就是 GPU 在 AI 里不可替代的原因。

完成判定

□ 能用自己的话说清训练和推理的区别，并各举一个运维场景　□ 能用自己的话讲清「这一册学的东西是什么、干什么用的」（见本册开篇）　□ 能说出显存和内存是两回事，各用什么命令看　□ 能用"博士 vs 小学生"讲清 GPU 为什么适合 AI（不掉进数学细节）

回滚方式：纯认知，无操作。

实战价值：工作里常问"你怎么理解 AI 运维和普通运维的区别"，答"推理服务在线上跑、显存是稀缺资源、训练任务要防中断"——三句话就把方向说对了。

8-02 用 Ollama 起一个本地模型并对话

为什么先做这一关：它零外部依赖：不抢 GPU、不花钱、断网也能跑（模型下载时除外）。先在自己机器上把"模型跑起来"这件事做成，再谈故障。

步骤 1：装并拉一个小模型

$ sudo apt install -y zstd                        # 新装 Ubuntu 没带 zstd，官方脚本解包会报 "requires zstd"
$ curl -fsSL https://ollama.com/install.sh | sh      # 官方一键脚本
$ ollama --version
ollama version is 0.3.14

$ ollama pull qwen2.5:1.5b        # 1.5B 的小模型，约 1GB，纯 CPU 也能跑
pulling manifest ...
success

$ ollama list
NAME             ID           SIZE    MODIFIED
qwen2.5:1.5b     a1b2c3d4e5f6  986 MB  10 seconds ago

解读：1.5B = 15 亿参数，属于"能塞进普通电脑"的体量。模型文件下载后存在本地（~/.ollama/models），之后断网也能用。

官方脚本拉不动？（国内网络常见）：curl -fsSL https://ollama.com/install.sh | sh 要连 ollama.com 下载二进制，线路不顺时会 SSL 断流、卡住不装。两条替代路径都免费，选一条：
① Docker 跑（推荐）——镜像可以走 7 册「开始之前」配好的加速器：docker run -d --name ollama -v ollama:/root/.ollama -p 127.0.0.1:11434:11434 ollama/ollama（端口安全写法：-p 11434:11434 会监听 0.0.0.0、整个局域网都能访问；写成 -p 127.0.0.1:11434:11434 才和原生安装一样只限本机）；之后每个命令加前缀 docker exec -it ollama（例：docker exec -it ollama ollama pull qwen2.5:1.5b）；"停服务"改 docker stop ollama（起回来 docker start ollama）。端口 11434、curl 接口与本关其余步骤完全一致；只有第 3 步的 ss -tulnp | grep ollama 会查不到——容器路线的监听者显示为 docker-proxy，改 ss -tulnp | grep 11434 就行。
② 离线包：找一台网络顺畅的机器下载 https://ollama.com/download/ollama-linux-amd64.tgz，拷到本机执行 sudo tar -C /usr -xzf ollama-linux-amd64.tgz；ollama run 会自动把服务带起来，"停服务"改 sudo pkill ollama。
两条都不通就先跳过安装别硬卡：本关"看端口 / curl 接口 / 停再起服务"的套路，先用 08 册 5-02 起的 Prometheus 当现成靶子练熟，等网络方便再回来补跑模型——8-06 的 --local 也一样，等模型就位再做。

步骤 2：对话

$ ollama run qwen2.5:1.5b
>>> 用一句话解释什么是运维
运维就是保证线上的服务一直能正常跑、出问题能尽快修好的那批人。
>>> /bye

解读：跑起来就像个聊天工具。但你要关注的不是聊天，是"这东西怎么对外提供服务"——它默认在本地开了个 HTTP 接口（下一关/下一册就用得上）。

步骤 3：看它开了什么端口（运维视角）

$ ss -tulnp | grep ollama
tcp   LISTEN 0 4096  127.0.0.1:11434  0.0.0.0:*  users:(("ollama",pid=3121,fd=3))

$ curl -s http://localhost:11434/api/generate -d '{"model":"qwen2.5:1.5b","prompt":"你好","stream":false}' | head -c 300
{"model":"qwen2.5:1.5b","created_at":"2026-10-09T22:40:11Z","response":"你好！有什么可以帮你的吗？",...}

解读：三件事：① 11434 是 Ollama 的默认端口（记住它，就像 9090 之于 Prometheus）；② 它只监听 127.0.0.1，所以只能本机访问（这是默认的安全设置）；③ 接口是 HTTP + JSON —— 跟 5-06 拉 Prometheus 指标是同一类活儿。

步骤 4：制造一次"服务没起来"（提前熟悉故障）

$ sudo systemctl stop ollama
$ curl -s http://localhost:11434/api/tags
curl: (7) Failed to connect to localhost port 11434: Connection refused
$ sudo systemctl start ollama && curl -s -o /dev/null -w "%{http_code}\n" http://localhost:11434/api/tags
200

解读：Connection refused = 端口没人听 = 服务没起来（对比 4-09 的端口排查链）。systemctl status ollama 能看到它为什么停。

完成判定

□ 模型拉下来并能对话（截图或记录一句回答）　□ 能说出模型文件放在哪、默认端口是多少、只听哪个地址　□ 能用 curl 调一次接口拿到 JSON　□ 能故意停掉服务、看到 Connection refused、再恢复

回滚方式：ollama rm qwen2.5:1.5b 删模型释放磁盘；systemctl stop ollama 停服务。

实战价值："你部署过模型吗"——"我用 Ollama 在本地跑过 1.5B 的小模型，知道它默认 11434 端口、只监听本地、模型文件在哪、怎么用 curl 调它"。这一串已经比大多数转行者强。

看什么含义 / 什么时候要盯它
GPU 型号（Tesla T4）不同型号显存和算力差很多；报工单时要写清型号
Driver / CUDA Version驱动版本决定了能跑什么框架版本 —— 这是环境不匹配的第一嫌疑人
Temp（42C）温度；长期高温（>80C）要查散热和负载
W / Cap（26W/70W）功耗与上限；"卡在跑但功耗很低"往往说明它在等数据（见 8-04 延伸）
Memory-Usage（412MiB/15360MiB）显存用了多少 / 总共多少——这一栏是 AI 运维最常盯的数字
GPU-Util（0%）算力利用率：高=在算，低=在等（等数据、等通信、等磁盘）

8-04 故意把显存撑爆：复现 CUDA out of memory（本册心脏）

为什么它是心脏：这类岗位更看重你面对没见过的故障，而不是背诵。OOM（显存溢出）是 AI 运维最高频、也最能讲出故事的故障——你要亲手把它造出来，读懂那段报错，再想出至少四种缓解办法。

环境兜底（抢不到免费卡也能完成本关）：本关要在真 GPU 上复现 OOM；配额用尽、平台排队时别干等——
① 同方法降级演练（推荐）：用 ulimit -v 先把试炼进程的内存上限压小、再申请超大内存，得到干净的 MemoryError：bash -c "ulimit -v 500000; python3 -c 'x = bytearray(20 * 1024**3)'"；想经历"被系统 OOM 杀"就用限内存容器（有 Docker 时）：docker run --memory=256m python:3.12 python3 -c 'x = bytearray(20 * 1024**3)'（退出码 137＝OOMKilled）——用同一套"现象 → 线索 → 建议"三层读法逐句拆，方法与 CUDA OOM 完全一致，只是换了故障现场。WSL 用户特别注意：别在本机直接"申请超大内存"赌系统杀进程——实测会把整个 WSL 发行版打挂（连接断开、容器与 k3s 全断）；要么像上面用 ulimit -v 限住，要么把演示关进限内存容器。
② 记录里如实标注："免费额度受限，未实测 CUDA，用内存 OOM 做了同方法演练"；
③ 对外就按记录说："CUDA OOM 我先用内存 OOM 做了同方法演练，三层读法一致；拿到卡 30 分钟能复现真版。"——如实说反而加分，硬吹最容易被追问拆穿。

步骤 1：把显存吃满

import torch
size = 20000                      # 先试 20000 × 20000
x = torch.randn(size, size, device="cuda")

RuntimeError: CUDA out of memory. Tried to allocate 1.49 GiB.
GPU 0 has a total capacity of 14.56 GiB of which 13.94 GiB is free.
Of the allocated memory 0 bytes is allocated by PyTorch,
and 12.31 MiB is reserved by PyTorch but unallocated.
If reserved but unallocated memory is large try setting
PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True to avoid fragmentation.

（这段是 PyTorch 的 CUDA OOM 报错；核心几句与新版本逐字一致，只有末尾 expandable_segments 那句的措辞新版略有改写——以你机器上的报错为准，读法不变。）

照做复现不了？上面这段报错来自一台显存已被占用的机器（示例）。在全新 Colab / Kaggle 的 T4（约 13.9 GiB 空闲）上，size = 20000（只申请 1.49 GiB）根本不会崩——把 size 继续加大到约 6.2 万（4 × 62000² ≈ 14.3 GiB）才会 OOM；想稳定复现也可以先占住一部分显存再跑。

逐句读这段报错（这就是"看懂报错"）：

原句它在说什么
Tried to allocate 1.49 GiB现象：这一次想申请 1.49G
total capacity of 14.56 GiB of which 13.94 GiB is free线索：卡上还有 13.94G 空闲 —— 不是"卡太小"：要么这次申请的块特别大，要么是碎片 / 别的进程占着把显存掏出了窟窿
0 bytes is allocated by PyTorch线索：PyTorch 自己还没占多少，说明是这一步的尺寸要得太狠
try setting PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True建议：官方给的缓解办法之一（治碎片化）

读报错三步法（读一行报错）：先看现象（要了多少、在哪失败）→ 再看线索（还剩多少、谁占的）→ 最后看建议（官方解法常常就写在最后几行）。14 册《日志报错解读》讲的就是这个顺序。

步骤 2：四种缓解办法，一个一个试

# 办法 1：把尺寸改小（最直接）
size = 12000
x = torch.randn(size, size, device="cuda")
print("占用：", round(torch.cuda.memory_allocated() / 1024**3, 2), "GiB")

# 办法 2：用完就释放（避免"垃圾"占着显存）
del x
torch.cuda.empty_cache()

# 办法 3：数据分批（batch 变小）—— 训练里最常用
# 原来一次喂 64 条 → 改成 16 条，显存占用大致降到 1/4

# 办法 4：治碎片化（报错里建议的那个环境变量）
# 注意：它只在"启动前"生效——写成启动命令的一部分最稳：
#   PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True python train.py
# 已经跑起来的会话里再改下面这行 os.environ，不会重新生效（要重启进程）
import os
os.environ["PYTORCH_CUDA_ALLOC_CONF"] = "expandable_segments:True"

解读：四种办法对应四种病因 —— 要得太多（尺寸）／没及时释放（泄漏）／一次喂太多（batch）／内存碎片（碎片化）。工作里常问"OOM 怎么处理"，按这四类答，就不会只答"换大卡"。

步骤 3：复现"明明还有显存却还是 OOM"

a = torch.randn(4000, 4000, device="cuda")   # 4000² × 4B = 64 MB ≈ 0.06 GiB
b = torch.randn(4000, 4000, device="cuda")
del a
b = b * 1.0                                   # 制造一些碎片
try:
    c = torch.randn(3000, 3000, device="cuda")
    print("这次成功")
except RuntimeError as e:
    print("失败：", str(e).splitlines()[0])
torch.cuda.empty_cache()                      # ← 关键动作
print("清理后：", round(torch.cuda.memory_reserved() / 1024**3, 2), "GiB 仍被保留")

解读：这就是报错里那句 "reserved but unallocated" 的真实含义 —— 显存被 PyTorch 抓着但没用上。看到这个关键词，第一反应就是 empty_cache() 或调 batch。

（这段是"演示"不是"必修"：这套 64MB 级的张量在 15GB 的 T4 上跑，大概率打印"这次成功"——碎片型 OOM 要接近满载时才会出现，小尺寸看到成功属正常；关键是理解 reserved 与 allocated 的差别。）

步骤 4：把这次排查写成记录（产出）

# 显存溢出排查记录
现象：报 CUDA out of memory，Tried to allocate X GiB
线索：报错里"还剩多少空闲"最关键 —— 剩得多说明要得太狠或碎片化；剩得少说明真不够
四类病因与对策：
  1) 尺寸/模型太大    → 减小输入、换更小模型、量化（参数用 8-bit 等低精度存，省显存）
  2) 没及时释放       → del + torch.cuda.empty_cache()
  3) 一次喂太多       → batch_size 调小、梯度累积
  4) 内存碎片         → PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True
验证：改完后跑通，并打印 memory_allocated() 确认占用在预期范围
一句话总结：OOM 先读"还剩多少"，再按四类病因对号入座

实战价值：这是整册最能讲的一关 —— "我故意复现过 CUDA OOM，能读懂报错的三层信息，并准备了四类缓解方案"。这是踩过的坑，不是背的文档（没抢到卡：按上方"环境兜底"如实说明口径）。

延伸：训练变慢了怎么拆（生产里最典型的"模糊故障"）

为什么单独讲它：前面几关的故障都是"坏了"（起不来、连不上）。而真实工作里更常见的是"没坏，但慢了"——没有报错、没有红灯，只有一句"今天训练怎么这么慢"。这类故障考的就是"把模糊问题拆成可验证的假设"，正是实际工作里最需要的能力。

分层拆法（从上到下，一层一层看）：

层先看什么慢了通常说明什么
① GPU 计算nvidia-smi 的 GPU-Util 是不是长期接近 100%长期 100% = 计算是瓶颈（正常情况）；很低 = GPU 在等数据/等通信，问题在下面几层
② 显存显存占用是否已接近上限、有没有 swap / OOM 前兆显存吃满会让框架反复腾挪、变慢（8-04 的 OOM 是它的极端形态）
③ 通信（多卡）NCCL 日志里各卡等待时间是否拉长某张卡拖后腿（慢卡/坏卡）会让所有卡一起等——木桶效应
④ 网卡 / 网络多机训练时网卡流量、是否有丢包/重传参数同步要走网络；网络抖动直接表现为"训练一步忽快忽慢"
⑤ 存储 / 读数据数据盘 IO、checkpoint 目录的写入速度checkpoint 写满带宽时，训练会明显卡顿（这就是为什么常看到"每存一次 checkpoint 就慢一下"）
⑥ 数据加载DataLoader 的 worker 数、CPU 是否打满读数据跟不上 GPU：GPU 利用率低 ＋ CPU 高，最典型的"饿着显卡"

怎么用它（假设 → 验证）：

现象：训练比昨天慢了一倍
假设 1：GPU 在等数据   → 验证：nvidia-smi 里 GPU-Util 只有 20%、CPU 打满 → 成立：加大 DataLoader worker
假设 2：某张卡拖后腿   → 验证：nvidia-smi 里 8 张卡里 1 张显存/利用率异常 → 成立：报修/换卡，先把它排除
假设 3：checkpoint 拖慢 → 验证：把保存间隔调长再跑一段，速度回升 → 成立：把 checkpoint 放到更快的盘 / 错峰

一句话记住：先分清是"GPU 在干活"还是"GPU 在等" —— 在干活（利用率高）说明瓶颈可能在计算本身；在等，就往"数据 / 通信 / 存储"三层去找。

实战价值：别人问"训练变慢你怎么查"，能答出这张分层表 ＋ "我先看 GPU 利用率再决定往哪层走"的人，就是在用运维的思维做 AI 运维。

顺带一提 · 断点续训（checkpoint / 断点续训）
是什么：训练过程中定期把"模型参数 ＋ 优化器状态 ＋ 走到第几步"存成文件（checkpoint）；万一机器挂了或者要停机维护，从最近一次 checkpoint 接着练，不用从头来。
为什么大模型必须要它：一次训练要跑几天到几个月、占用成百上千张卡 —— 中途不出任何问题几乎不可能。没有它，一次断电就等于烧掉几百万。所以"能不能从断点恢复"是大模型训练的生死线。
真要用时去哪查：搜"PyTorch checkpoint resume training"或"deepspeed save_checkpoint"；顺手记一句：存 checkpoint 会抢磁盘带宽，所以经常能看到"每存一次就慢一下"（这正是上面那张分层表第 ⑤ 层）。
顺带一提 · NCCL 通信延迟抖动 与 checkpoint 耗时
NCCL 是什么：多张卡之间"对答案"用的通信库（集合通信）。各卡算完一批梯度要互相汇总，谁慢了大家都得等——所以叫"通信延迟抖动"。
为什么要盯它：训练忽快忽慢、多卡利用率参差不齐，很多时候根因就在通信上（某张卡慢、某条链路抖），而不是模型的问题。生产里的日常，盯的就是它们。
checkpoint 耗时：写一次 checkpoint 会同时吃掉存储带宽，短则几秒、长则几十秒，期间训练几乎停顿 —— 高频保存会明显拉低整体吞吐。
真要用时去哪查：搜"NCCL debug log"（设 NCCL_DEBUG=INFO 看每步耗时）和"checkpoint 加速"（异步保存 / 更快的数据盘）；先知道有这两个东西、知道它们会拖慢训练，就够这一轮用了。

8-05 跑一个最小训练

为什么只跑两轮：你不需要学会训练模型 —— 只需要"跑过一次真的训练"，这样 8-04 的显存问题才有具体场景，聊起来也能说“训练和推理我都见过”。所以就用最小的 MNIST，两轮收工。

步骤 1：两轮训练跑起来

import torch
from torch import nn
from torch.utils.data import DataLoader
from torchvision import datasets, transforms

tf = transforms.ToTensor()
train = datasets.MNIST(root="./data", train=True, download=True, transform=tf)
loader = DataLoader(train, batch_size=64, shuffle=True)

model = nn.Sequential(nn.Flatten(), nn.Linear(784, 128), nn.ReLU(), nn.Linear(128, 10)).cuda()
opt = torch.optim.Adam(model.parameters(), lr=1e-3)
loss_fn = nn.CrossEntropyLoss()

for epoch in range(2):                      # 就两轮
    for i, (x, y) in enumerate(loader):
        x, y = x.cuda(), y.cuda()
        loss = loss_fn(model(x), y)
        opt.zero_grad(); loss.backward(); opt.step()
        if i % 200 == 0:
            print(f"epoch {epoch} step {i} loss {loss.item():.3f}")

epoch 0 step 0 loss 2.315
epoch 0 step 200 loss 0.421
...
epoch 1 step 800 loss 0.187

解读：loss 在往下走 = 训练在正常进行（2.3 → 0.19）。这一步只要跑得通、看得懂 loss 下降，就达标了。

步骤 2：脚本（两种后端都支持，可直接复制）

#!/usr/bin/env python3
"""命令行小助手：--ask "问题"；默认走 DeepSeek，--local 走本地 Ollama"""
import argparse
import json
import logging
import os
import sys

import requests

DEEPSEEK = "https://api.deepseek.com/chat/completions"
OLLAMA = "http://localhost:11434/api/generate"


def ask_deepseek(prompt, timeout=30):
    key = os.environ.get("DEEPSEEK_API_KEY")
    if not key:
        raise RuntimeError("没有找到 DEEPSEEK_API_KEY（见步骤 1）")
    resp = requests.post(
        DEEPSEEK,
        headers={"Authorization": f"Bearer {key}", "Content-Type": "application/json"},
        json={"model": "deepseek-chat",
              "messages": [{"role": "user", "content": prompt}]},
        timeout=timeout,
    )
    resp.raise_for_status()
    data = resp.json()
    return data["choices"][0]["message"]["content"]


def ask_local(prompt, timeout=120):
    resp = requests.post(OLLAMA, json={"model": "qwen2.5:1.5b",
                                       "prompt": prompt, "stream": False}, timeout=timeout)
    resp.raise_for_status()
    return resp.json()["response"]


def main():
    p = argparse.ArgumentParser(description="命令行小助手")
    p.add_argument("--ask", required=True, help="要问的问题")
    p.add_argument("--local", action="store_true", help="改用本地 Ollama")
    p.add_argument("--timeout", type=int, default=30)
    args = p.parse_args()

    logging.basicConfig(filename=os.path.expanduser("~/assistant.log"), level=logging.INFO,
                        format="%(asctime)s %(levelname)s %(message)s")
    try:
        answer = ask_local(args.ask, args.timeout) if args.local else ask_deepseek(args.ask, args.timeout)
    except Exception as exc:
        logging.error("调用失败：%s", exc)
        print(f"[错误] {exc}", file=sys.stderr)
        return 1
    logging.info("问：%s｜答：%s", args.ask, answer[:80])
    print(answer)
    return 0


if __name__ == "__main__":
    sys.exit(main())

解读（三处关键）：① key 从环境变量读，不写进代码；② 两种后端用一个开关切换——没 key 时用 --local 照样能跑通，这就是 8-02 那一关的价值；③ 异常与日志走 3-09 的套路，退出码 0/1。

8-08 把 GPU 指标接进监控面板

解读：DCGM_FI_DEV_GPU_UTIL = 利用率，FB_USED / FB_FREE = 显存已用 / 剩余（单位 MiB）。这些数字就是 nvidia-smi 背后读的东西——现在它们变成了可以让 Prometheus 抓的接口。

8-09 读 DeepSeek-V3 技术报告，写 MoE / MLA 中文笔记

（参考：DeepSeek-V3 Technical Report，arxiv.org/abs/2412.19437。不读原文也能完成本关：用下面的大白话小节 ＋ 8-06 的命令行助手提问就能把笔记写完。）

这一关不是让你啃论文，而是回答"聊聊你对 AGI 的理解"。你只需要用自己的话讲清两个词，再补一点自己的疑问。

步骤 1：先建立"大模型很贵"的直觉

模型越大 → 参数越多 → 显存越吃紧、算得越慢、花钱越多
于是大家想两件事：
  ① 怎么让**参数多但每次只用一部分**？ → 这就是 MoE
  ② 怎么让**长文本不要太占显存**？     → 这就是 MLA

解读：先有这个直觉，再看术语就不会晕 —— MoE 和 MLA 都是"省"的招数，一个省算力，一个省显存。

步骤 2：两个词的大白话版

词大白话为什么 AI 运维要懂
MoE
（混合专家）		模型里有很多"专家小组"，来一个问题只叫相关的几个专家干活，其他不动 —— 参数量可以做到很大，但每次只跑一小部分它决定了显存占用和显存分布：专家要分散在不同卡上，专家之间的调度和通信就是运维要盯的东西
MLA
（多头潜在注意力）		把"注意力"要记的东西压缩后再存，同样长的上下文，占的显存小很多它直接影响长文本能不能跑得起来：同样的卡，能不能开更长的上下文

遇到不懂的词（KV cache、注意力、token…）别去啃整篇论文 —— 用 8-06 的那个命令行助手问一句"用大白话解释 KV cache 是什么"，然后记下来。

步骤 3：写一页笔记（产出）

# DeepSeek-V3 技术报告读书笔记
1) 它想解决什么：参数规模大 → 训练和推理都贵
2) MoE 用它干什么：参数多、但每次只激活一部分（省钱、省算力）
3) MLA 用它干什么：压缩注意力的存储（省显存、能开更长上下文）
4) 和运维的关系：专家怎么分布到多卡、显存怎么切、通信怎么不拖后腿
5) 我自己的疑问（至少一条）：比如"专家分布不均会不会导致某张卡特别忙？"
—— 疑问比结论更值钱，聊起来最有料的就是它

完成判定

□ 能用大白话讲清 MoE 和 MLA 各解决什么问题（不背定义）　□ 能说出它们和"显存 / 卡 / 通信"的关系　□ 有一页中文笔记（含至少一条自己的疑问）　□ 至少用命令行助手查过两个不懂的词

回滚方式：纯阅读与笔记，无风险。

实战价值：工作里聊到 AGI 理解，靠的就是这个。能说"我读过 DeepSeek-V3 的报告，我理解 MoE 是让参数大但每次只用一部分，MLA 是省显存；我有个疑问是专家分布不均会不会拖慢训练"——带着疑问的答案，比背书好听得多。

8-10 画一张全景图，讲 10 分钟（★）

为什么这一关是 ★：这类岗位的要求里写着"脑子里要有从 GPU 计算 → 显存 → NVLink → 网卡 → 存储 → 调度的完整地图"。这不是加分项，是入场要求。这一关就是把这十关学的东西压缩成一张图，练到能讲 10 分钟。

步骤 1：照这六层画（一层一行，别抄术语，用你自己的话）

① GPU 计算      —— 卡在不在干活？（nvidia-smi: GPU-Util；工具：8-03）
② 显存          —— 装得下吗？（FB_USED/FB_FREE；故障：OOM，8-04）
③ NVLink / 卡间  —— 多卡之间怎么快速换数据（同一台机器内的"高速通道"）
④ 网卡 / 网络    —— 多机之间怎么同步（NCCL 走网络；抖动会让所有卡一起等）
⑤ 存储          —— 数据和 checkpoint 从哪来、写多快（写 checkpoint 会抢带宽）
⑥ 调度          —— 谁来分配这些卡和资源（K8s 的 requests/limits，6-07）

画法建议：一张 A4 横放，左边画这条"从算力到调度"的竖线，右边每一层挂上：① 看什么指标 ② 出问题什么样 ③ 我练过哪一关。手画比打字好（讲的时候指着说）。

步骤 2：每层准备一个"这里会出什么问题"

① GPU 计算：利用率常年个位数 → 在等数据（查 DataLoader / CPU）
② 显存：      OOM → 尺寸/batch/碎片/泄漏四类病因（8-04 的记录直接搬过来）
③ NVLink：    某张卡慢 → 所有卡跟着等（木桶效应）
④ 网络：      训练一步忽快忽慢 → 通信延迟抖动（NCCL 日志）
⑤ 存储：      每存一次 checkpoint 就卡一下 → 存储带宽被抢
⑥ 调度：      Pod 一直 Pending → requests 要得比节点能给的多（6-07 见过）
