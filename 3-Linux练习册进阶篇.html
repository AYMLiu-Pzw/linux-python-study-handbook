场景 1｜本地推理服务起不来（日志排查）

📋 背景工单：你是某公司 AI 组的新运维。同事说他昨天在服务器上装了一个推理服务，今天早上启动失败，让你去处理。机器上有个服务脚本 labservice.sh（见附录 A），它在某个目录下写日志。

🔧 场景搭建手册（做题前执行）：

$ mkdir -p ~/lab && cd ~/lab
# 只检查并停止本场景记录的 PID；不要按模糊命令名误杀其他服务
$ if [ -f ~/lab/labservice.pid ]; then old_pid=$(cat ~/lab/labservice.pid); ps -p "$old_pid" -o pid=,args=; fi
$ ./labservice.sh stop 2>/dev/null || true
$ nano labservice.sh     # 把附录 A1 的脚本内容全部粘贴进来，保存退出（Ctrl+X → Y → 回车）
$ nano labservice.conf   # 把附录 A2 的配置内容粘贴进来，LOGDIR 填你的真实路径（用 A2 里的生成命令产生）
$ chmod +x labservice.sh
$ ./labservice.sh start &       # 后台启动（末尾加 &，不占终端），先确认它本来是好的
$ sleep 1 && ./labservice.sh status # 应显示：运行中：父进程 PID=…，端口=8080
$ ./labservice.sh stop         # 停掉它：子服务已停、PID 文件已清理（正常停止，日志不会写 ERROR）
$ ss -tlnp | grep 8080         # 无输出 = 端口已释放（确认干净后再继续）
# 现在注入故障：把 labservice.conf 里 PORT=8080 改成 PORT=abc（非法配置）
$ ./labservice.sh start        # 启动失败（返回非 0）——故障现场就位，开始做题

故障原理：日志目录里会留下 1 行真正的根因（[ERROR] 端口配置非法），其余都是干扰行。

编号目标（只给这些）
进1-1确认服务当前状态：进程在不在、端口有没有在监听
进1-2找到日志文件的位置，从中定位出"根本原因那一行"，并说明你是怎么排除其他干扰行的
进1-3修复问题，重新启动服务，让服务成功跑起来
进1-4验证服务可用（端口通了、日志显示正常），写一份 3 行的处理记录（做了什么、为什么）

最终产出：一份故障处理记录 + 复述"处理流程四步（确定时间窗口 → 收集日志/状态/退出码 → 结合上下文定位 → 修复并复测）"。

场景 2｜磁盘满应急（模型文件占满磁盘）🌐

📋 背景工单：你负责的 GPU 服务器磁盘使用率报警到 92%，同事说服务开始写日志报"空间不足"。你的任务：定位是什么占满了磁盘、安全清理、恢复服务、给出预防措施。

🔧 搭建手册（做题前执行，需电脑 Ubuntu 🌐）：

# ① 先确认磁盘空间（df -h ~），再创建一个 500MB 空白镜像。
⚠️ 空间紧张的替代参数（二选一，直接照抄整组；均为 Ubuntu 22.04 / ext4 / mount -o loop 实测值）：
#   替代1：count=250（250MB 镜像）+ 塞入量合计 180MB，六个塞入行示例：30M、30M、30M、30M、30M、30M。实测 df 约 219M/181M/21M、Use% 90%，以你机器 df 实测为准。
#   替代2：count=150（150MB 镜像）+ 塞入量合计 100MB，六个塞入行示例：20M、20M、20M、10M、10M、20M。实测 df 约 125M/101M/14M、Use% 88%，以你机器 df 实测为准。
$ df -h ~
$ dd if=/dev/zero of=~/lab/disk.img bs=1M count=500
# ② 格式化成 ext4 文件系统（在镜像里格式化，真磁盘不受影响）
$ mkfs.ext4 ~/lab/disk.img
# ③ 挂载成独立分区（需要 sudo；loop 让文件伪装成磁盘）
$ sudo mkdir -p /mnt/lab
$ sudo mount -o loop ~/lab/disk.img /mnt/lab
# ④ 塞入"故障文件"：模型文件、旧日志、缓存各一堆，直到接近写满
$ sudo mkdir -p /mnt/lab/models /mnt/lab/logs /mnt/lab/cache
$ sudo fallocate -l 70M /mnt/lab/models/model_v1.bin
$ sudo fallocate -l 70M /mnt/lab/models/model_v2.bin
$ sudo fallocate -l 60M /mnt/lab/logs/old_service.log
$ sudo fallocate -l 60M /mnt/lab/cache/tmp_cache.bin
$ sudo fallocate -l 70M /mnt/lab/logs/old_service2.log
$ sudo fallocate -l 70M /mnt/lab/cache/tmp2.bin # 合计 400M；500M 镜像实测（Ubuntu）格式化后约 Size 452M、写满后 Used 约 401M、Avail 约 17M、Use% 约 96%。预期 Use% 约 95%~97%，以你机器的 df 实测为准——最后一条 fallocate 成功即搭建成功（Avail 剩十几 M 属正常：这正好复现“磁盘即将写满”）
$ df -h /mnt/lab        # 确认接近写满：预期 Use% 约 95%~97%，以你机器的 df 实测为准（>85% 即搭建成功），现场搭建完成
⚠️ 安全提示：故障全部发生在 /mnt/lab 这个镜像分区里。做完题执行 sudo umount /mnt/lab 卸载后，一切恢复原样，真系统没有任何变化。

题目：进2-1 确认是哪个挂载点满了，占用多少。进2-2 进入该分区，逐层定位最大的目录、最大的文件。进2-3 判断哪些可安全删除、哪些不能动（说清依据），完成清理。进2-4 验证恢复，写出 2 条预防措施。

场景 3｜服务连不上（网络链路排查）

📋 背景工单：同事反馈"我们部署在本地 8080 端口的服务突然连不上了"，让你按链路排查：主机通不通 → 端口通不通 → 服务进程在不在 → 日志怎么说。

🔧 场景搭建手册：在本机用 labservice.sh 起一个服务，然后从三种故障里任选一种注入（做两遍可以换着来）：

$ cd ~/lab
# 故障 A：服务压根没起（什么都不做，直接进入题目）
# 故障 B：服务起了，但端口被别的进程占了：
$ python3 -m http.server 8080 &      # 先用 Python 起一个简易网页服务，占住 8080 端口
HTTP_PID=$!                        # 记下它的 PID，做完题只停它，别误伤别的 Python 服务
$ ./labservice.sh start             # 服务启动失败 → 端口冲突
# 故障 C：服务正常但监听了错误的地址——把 labservice.sh 里这一行：
#   python3 -m http.server "$PORT"
# 改为（--bind = 指定只监听哪个地址；此写法让它只监听本机回环地址）：
#   python3 -m http.server --bind 127.0.0.1 "$PORT"
# 然后用"另一台设备"访问这台机器的局域网 IP 测试（单机用户可用平板连电脑 IP；
# 不方便时跳过 C，只做 A、B 两种故障）单机自测法：没有第二台设备时，用 ip addr 查本机局域网 IP，再 nc -zv 本机IP 8080——同样得到 refused，不用真找另一台设备。

新命令介绍：nc（netcat，网络工具）——nc -zv 主机 端口 用来测试"端口到底通不通"。若提示 nc 不存在，先 sudo apt install netcat-openbsd。

编号目标（只给这些）
进3-1用 ping（测试主机可达性）确认主机可达性（含 ping localhost 与 ping 网关的区别）
进3-2用 ss -tlnp（查看监听端口）查看监听端口，判断目标端口有没有在听、被谁听
进3-3用 nc -zv 或 curl 实测端口通不通，把"进程在听"和"真的能连上"分开判断
进3-4定位故障点，修复，并复述分层排查：回环/网关 → 目标主机 → 端口/应用 → 进程/日志，同时说明每层结论的边界

最终产出：一份网络故障排查记录 + 画一张排查顺序流程图。

场景 4｜服务与进程运维（含 GPU 进程定位）

📋 背景工单：你在管一台"推理服务机器"，今天要完成：部署一个服务并让它开机自启、监控它、处理一个"卡死进程"，最后查清楚"显卡/文件被哪个进程占着"。

📌 环境边界（实测结论）：① GPU 题（进 4-3）是 NVIDIA 外部扩展：需 NVIDIA 显卡 + 驱动 + nvidia-smi；fuser 需先 sudo apt install psmisc。无 GPU 就做替代题（fuser -v 查文件占用），替代题通过 ≠ GPU 题通过。② systemd 题（进 4-4 开机自启）：完整验证需 Ubuntu 主机 systemd（Restart=on-failure 已在 Ubuntu 22.04 + systemd 实测通过：外部 kill -9 子服务后 unit 自动重启（MainPID 变化、NRestarts 递增、端口恢复）；systemctl stop 后 unit inactive、不误触发重启）；WSL 可能可用，容器 PID 1 非 systemd 时 systemctl 为 offline，不能替代主机验收。实验边界：Ubuntu + systemd + sudo + 专用实验机，完整走 start → 验证 → stop → 清理；正常 stop 后 unit 应为 inactive。受限环境都如实记为“环境限制”，不影响其余题目。

🔧 场景搭建手册：

$ cd ~/lab
$ ./labservice.sh start &                 # 只启动本场景服务
$ nohup ./loop.sh > loop.log 2>&1 & echo $! > loop.pid # 保存 loop.sh 的 PID
$ top                                      # 现场就位

收尾：读取 loop.pid，先用 ps -p PID -o pid=,args= 核对命令归属，再按 PID 停止；执行 ./labservice.sh stop 停止本场景服务；最后删除 loop.pid、loop.log 和服务 PID 文件。本练习不使用按模糊命令名清理的方式。

编号目标（只给这些）
进4-1部署服务：后台运行 + 确认进程和端口都正常
进4-2用 top/ps 找出那个死循环进程，优雅终止它（并说明为什么不直接 -9）
进4-3GPU 题：用 nvidia-smi 查看显卡状态，用 fuser -v 定位占用显卡的进程并处理。/ 无 GPU 替代题：定位"占用某个文件"的进程并处理（技能完全等价）
进4-4 🌐设置服务开机自启（systemd 写 unit 文件 / 或 rc.local / 或说明其他方式），重启验证自启生效

最终产出：一台"服务能自启、能监控、出问题会处理"的练习机状态 + 处理记录。

场景 1 答案

【进 1-1】确认服务状态

① 先想什么："服务起没起"要回答两个问题：进程活着吗？端口在听吗？

② 为什么用这个命令：ps aux | grep labservice 看进程；ss -tlnp 看所有监听端口（-t TCP、-l 监听、-n 数字显示、-p 显示进程名）。

③ 完整步骤： style="break-after: avoid; page-break-after: avoid;"

$ ps aux | grep -v grep | grep labservice   # 无输出 = 进程没活
$ ss -tlnp | grep 8080                    # 无输出 = 没人监听 8080

④ 怎么验证做对了：两个命令都无输出，确认"进程没起、端口没听"——故障实锤，不是"起了但连不上"。

【进 1-2】定位根因行

① 先想什么：日志在哪？哪一行是根因、哪些是干扰？——看脚本配置找日志位置，再按"级别"过滤。

② 为什么用这个命令：日志位置在 labservice.conf 的 LOGDIR 里（或脚本中写死）。用 tail -n 20 看最后几行（启动失败的信息都在末尾），重点看 [ERROR] / [FATAL] 行，忽略 [INFO] 心跳行。

③ 完整步骤： style="break-after: avoid; page-break-after: avoid;"

$ cat labservice.conf             # 找到 LOGDIR= 那一行，记下它的值（应是你的真实路径）
$ tail -n 20 ~/lab/logs/labservice.log
... [INFO] 服务启动中，配置端口=abc
... [ERROR] 端口配置非法: abc（必须是数字）   ← 根因就是这一行
$ grep -e ERROR -e FATAL ~/lab/logs/labservice.log   # 一步过滤出根因（-e = 每个 -e 后跟一个匹配模式，可一次搜多个词）

④ 怎么验证做对了：你能说出"为什么排除其他行"——[INFO] 心跳行是每 3 秒一条的噪音，[ERROR] 只在出问题时出现。处理流程四步：确定时间窗口 → 收集日志/状态/退出码 → 结合上下文定位 → 修复并复测。

【进 1-3】修复并重启

① 先想什么：根因是"端口配置非法"，修复 = 把配置改回合法值。

② 为什么用这个命令：改配置用 nano 编辑 labservice.conf（nano 按键：改完 Ctrl+X → Y → 回车），把 PORT=abc 改回 PORT=8080，再重新启动。

③ 完整步骤： style="break-after: avoid; page-break-after: avoid;"

$ nano labservice.conf   # 改完 Ctrl+X → Y → 回车        把 PORT=abc 改回 PORT=8080，保存退出
$ ./labservice.sh start
$ ps aux | grep -v grep | grep labservice   # 进程活了

④ 怎么验证做对了：进程存在，且日志末尾出现 [INFO] 服务启动成功。修复不是"猜"，是"改掉日志指出的那一处"。

【进 1-4】验证 + 处理记录

① 先想什么：验证要"从外到内"——端口通不通（外部视角）、日志正不正常（内部视角）。

② 为什么用这个命令：curl localhost:8080 或 nc -zv localhost 8080 测端口；tail -f 看心跳在跳。

③ 完整步骤： style="break-after: avoid; page-break-after: avoid;"

$ nc -zv localhost 8080              # Connection to localhost 8080 port [tcp/*] succeeded!
$ tail -f ~/lab/logs/labservice.log  # 每 3 秒一条心跳，Ctrl+C 退出

④ 怎么验证做对了：端口连通 + 心跳正常，服务恢复。处理记录示例（3 行）：
1. 现象：服务启动失败。
2. 定位：日志 [ERROR] 端口配置非法（PORT=abc）。
3. 处理：改回 PORT=8080 重启，端口 8080 连通、心跳正常。已提醒同事：改配置后保存前核对格式。

场景 2 答案

① 先想什么：磁盘满分两层看——"全局"（哪个分区满）用 df -h，"局部"（谁占的）用 du 一层层下钻，最后用 ls -lhS 按大小排序找元凶。清理前必须判断文件性质：model_v1.bin 是被 v2 替代的旧模型（可删），old_service.log 是旧日志（可删），tmp_cache.bin 是缓存（可删）；但如果服务正在写某个日志，那个就不能删。注意：这些文件是搭建手册用 sudo fallocate 创建的（root 属主、目录 root 可写），普通用户直接 rm 会 Permission denied——删除也要 sudo。

场景 3 答案

【进 3-1】主机可达性

① 先想什么：连不上先从最底层查起——机器本身通不通。

② 为什么用这个命令：ping localhost 只测回环和本机网络栈，不能证明网卡、网关或外网正常；ping 网关IP 才是局域网层测试，但 ICMP 可能被防火墙禁用。网关地址用 ip route 查。再逐步测试目标 IP、端口和应用，不能只凭一次 ping 下结论。

③ 完整步骤： style="break-after: avoid; page-break-after: avoid;"

$ ping -c 4 localhost      # 4 个包，全通
$ ip route                # 找到默认网关地址
$ ping -c 4 网关IP        # 局域网通

④ 怎么验证做对了：输出显示 0% packet loss。本场景是"本地 8080 服务"，ping 通说明问题在更高层（端口/进程/配置），继续下一题。

【进 3-2】端口监听检查

① 先想什么：8080 有没有人在听？被谁听？

② 为什么用这个命令：ss -tlnp 列出所有 TCP 监听端口及进程。故障 A（没起）→ 无 8080；故障 B（被占）→ 8080 有监听但进程是 http.server 不是 labservice。

③ 完整步骤： style="break-after: avoid; page-break-after: avoid;"

$ ss -tlnp | grep 8080
# 故障A：无输出 → 服务没起
# 故障B：LISTEN 0 5 0.0.0.0:8080 ... users:(("python3",...)) → 被 python3 占着

④ 怎么验证做对了：能根据 ss 输出判断出"没起"还是"被占"，并说出占用进程是谁——这一步直接决定下一步动作（启动 vs 杀占用者）。

【进 3-3】实测连通

① 先想什么："进程在听"不等于"真的能连上"——防火墙、监听地址都可能让"听着却连不上"。

② 为什么用这个命令：nc -zv 主机 端口 直接发起一次连接尝试（z=只测不传数据，v=显示过程）；curl 还能顺带看服务是否正常应答。

③ 完整步骤： style="break-after: avoid; page-break-after: avoid;"

$ nc -zv localhost 8080
# 能连：Connection to localhost 8080 port succeeded!
# 不能连：Connection refused（没人听）或 timeout（有防火墙丢包）
$ curl -I localhost:8080    # 看 HTTP 响应头，确认服务正常应答

④ 怎么验证做对了：能区分三种结论——refused（没进程听）、timeout（防火墙/地址错）、succeeded（连通）。故障 C（监听地址错）的表现正是"localhost 能连、真实 IP 连不上"。

【进 3-4】定位 + 修复 + 复述顺序

① 先想什么：把前三题的结论拼起来，按"主机→端口→进程→日志"给故障点定位。

② 为什么用这个命令：A 类修复=启动服务；B 类修复=找到占用者（ss 输出里有 PID）评估后 kill 掉、再启动服务；C 类修复=改回正确的监听地址。

③ 完整步骤： style="break-after: avoid; page-break-after: avoid;"

# 故障B 修复示例：
$ ss -tlnp | grep ':8080'          # 先看原始输出，PID 在 users:(("python3",pid=1234,...)) 里
$ PIDS=$(ss -tlnp | grep ':8080' | sed -n 's/.*pid=\([0-9][0-9]*\).*/\1/p')   # 提取全部 PID
$ N=$(echo "$PIDS" | sed '/^$/d' | wc -l)   # 统计个数
$ if [ "$N" -ne 1 ]; then echo "检测到 $N 个进程占用 8080：$PIDS ——先列出来人工判断，停止处理"; exit 1; fi   # 不是唯一 PID 就停，绝不自动取第一个
$ OCC_PID="$PIDS"
$ ps -p "$OCC_PID" -o pid=,args= | grep -q "python3 -m http.server 8080" || { echo "PID $OCC_PID 的命令行不是本场景的 http.server，停止处理"; exit 1; }   # 核对命令行确实是本场景进程才动手
$ kill "$OCC_PID"                    # 先优雅终止
$ ./labservice.sh start         # 重启服务
$ nc -zv localhost 8080         # 验证连通

④ 怎么验证做对了：服务连通。四步顺序脱口而出：先记录各层证据，再按“确定时间窗口 → 收集日志/状态/退出码 → 结合上下文定位 → 修复并复测”处理，不能只凭单次 ping 或单条命令下结论。

场景 4 答案

【进 4-1】部署 + 确认

① 先想什么：部署 = 后台跑起来 + 退出终端也不死。

② 为什么用这个命令：nohup 命令 & 让进程忽略挂断信号（终端关了它也不死）；确认用 ps + ss 双保险。

③ 完整步骤： style="break-after: avoid; page-break-after: avoid;"

$ nohup ./labservice.sh start &
$ ps aux | grep -v grep | grep labservice   # 在

④ 怎么验证做对了：进程和端口双重确认。完成后用本场景 PID 停止服务，再检查 PID 文件、端口和进程均已消失；日志本体在 LOGDIR 里。

【进 4-2】揪出死循环进程

① 先想什么：死循环通常会持续占用 CPU；先用资源观察确认，再只操作本场景保存的 PID。

② 为什么用这个命令：top 按 P 观察高 CPU 进程；loop.pid 是搭建时记录的本场景 PID。先发 TERM 给程序清理机会；实验脚本会用 trap 忽略 TERM，所以确认仍在后才使用 KILL。

③ 完整步骤： style="break-after: avoid; page-break-after: avoid;"

$ loop_pid=$(cat loop.pid)
$ ps -p "$loop_pid" -o pid=,args= # 必须确认命令行属于 loop.sh
$ kill "$loop_pid"
$ ps -p "$loop_pid" # 仍在运行才进行下一步
$ kill -9 "$loop_pid" # 最后手段
$ rm -f loop.pid loop.log
$ top # CPU 应降回正常水平

④ 怎么验证做对了：确认 loop.sh 的 PID 已不再存在、CPU 占用下降、loop.pid 已删除。不能根据 PID 文件直接杀进程，必须先用 ps 核对命令归属，防止 PID 复用误杀其他进程。

【进 4-3】GPU / 文件占用定位

① 先想什么：GPU 显存被谁占着？——技能本质是"资源 → 占用它的进程"。

② 为什么用这个命令：nvidia-smi 看显存使用和占用进程 PID；fuser -v /dev/nvidia* 反查"谁占着 GPU 设备"。无 GPU 的等价题：fuser -v 某个文件 反查"谁占着这个文件"——命令和思路完全一样。

③ 完整步骤： style="break-after: avoid; page-break-after: avoid;"

$ nvidia-smi                    # GPU 题：看 Processes 区块里的 PID
$ fuser -v /dev/nvidia*         # 哪个进程占着 GPU
$ fuser -v ~/lab/logs/labservice.log # 无 GPU 替代：哪个进程占着这个文件（选正被进程打开的文件——labservice.log 被 python3 持续打开着）

④ 怎么验证做对了：fuser 输出"文件: 进程名(PID)"格式，与 ps 结果互证。fuser 只显示"打开着该文件"的进程——所以要做实验，得选一个正被进程持续打开的文件（如服务的日志），而不是写完就关的 pid 文件。核心能力不是记命令，是"从资源反查进程"这个思路——磁盘满（du 找文件）、端口被占（ss 找进程）、GPU 被占（fuser），同一种思维。

【进 4-4 🌐】开机自启

① 先想什么：让 systemd 这个大管家替你"开机自动拉起服务"。

② 为什么用这个命令：写一个 unit 文件描述服务，systemctl enable 注册开机自启，systemctl start 立即生效。无 systemd 的环境说明 rc.local 或 crontab @reboot 方案即可。

③ 完整步骤： style="break-after: avoid; page-break-after: avoid;"

$ EXEC_PATH="$(readlink -f ~/lab/labservice.sh)"   # 先拿真实绝对路径（readlink -f 把 ~ 展开成完整路径）
$ echo "$EXEC_PATH"                              # 只看一眼，确认输出是完整真实路径（这一步就是用它替换下面 %s 的值）
$ printf '[Unit]\nDescription=Lab fake service\n[Service]\nExecStart=%s start\nRestart=on-failure\nRestartSec=2\n[Install]\nWantedBy=multi-user.target\n' "$EXEC_PATH" | sudo tee /etc/systemd/system/labservice.service >/dev/null   # 动态生成 unit，不手写占位路径
$ sudo systemctl daemon-reload
$ sudo systemctl enable --now labservice
$ sudo reboot          # 重启验证（会断开当前所有连接：先在本地终端做，或改用 sudo systemctl restart labservice 代替，效果等价）
$ systemctl status labservice   # active (running) = 自启成功
$ sudo systemctl disable --now labservice && sudo rm /etc/systemd/system/labservice.service && sudo systemctl daemon-reload   # 练习完恢复原状：先 disable 停止、再删 unit、最后 daemon-reload 让 systemd 重新读配置

④ 怎么验证做对了：重启后服务自动在跑。养成习惯：改完 unit 文件必须 daemon-reload，这是新手最容易漏的一步。

Restart=on-failure 验证（Ubuntu 22.04 + systemd 实测通过，实测现象附在各步骤后）：

$ sudo systemctl start labservice
$ ss -tlnp | grep :8080   # 输出如 users:(("python3",pid=1234,...))——记下这个唯一 PID
⚠️ 安全警告：不要用 pkill -f 'http.server 8080'——它按整条命令行模糊匹配，会误杀别的同名 http.server。
$ PID=1234   # 换成上一步 ss 显示的唯一 PID（如 ss 显示多个 pid，先逐个 ps 核对，只处理本场景那个）
$ ps -p "$PID" -o pid=,args=   # 人工核对命令行确实是本场景子服务（含 http.server 8080），不是别的进程
$ sudo kill -9 "$PID"   # 只杀这一个 PID；父服务随后以非 0 退出，触发 Restart=on-failure
$ for i in $(seq 1 30); do systemctl is-active --quiet labservice && ss -tlnp | grep -q :8080 && break; sleep 1; done   # 轮询最多 30 秒：等 unit 恢复 active 且端口恢复（实测恢复约需 4~5 秒，固定 sleep 2 会看到“还没恢复”的假象）
$ systemctl status labservice   # 预期：状态仍为 active (running)，Main PID 变了
$ journalctl -u labservice -n 10          # 预期：看到“已重启”相关日志，NRestarts ≥ 1

① 先想什么：把三个手动命令装进一个文件，开头声明解释器。

② 为什么用这个命令：df（磁盘）、free（内存）、uptime（负载）都是"看一眼"类命令，脚本就是它们的组合 + 中文注释。

【进 5-2】服务健康检查脚本

① 先想什么："健康"要查三层：进程在不在、端口通不通、日志新不新。

② 为什么用这个命令：读 labservice.pid + ps 核对命令行查进程（不用 pgrep -f，避免误匹配同名脚本）；nc -z 查端口；stat -c %Y 日志文件 拿日志最后修改时间，和当前时间比较判断"最近有没有更新"。

③ 完整步骤： style="break-after: avoid; page-break-after: avoid;"

$ nano health_check.sh # 写完 Ctrl+X → Y → 回车保存退出
#!/bin/bash
LOG=~/lab/logs/labservice.log
[ -f ~/lab/labservice.pid ] || { echo "进程：PID 文件不存在，服务没在运行"; exit 1; }
PID=$(sed -n '1p' ~/lab/labservice.pid)
SPATH=$(sed -n '2p' ~/lab/labservice.pid)
INSTDIR=$(sed -n '3p' ~/lab/labservice.pid)
TARGET_SH=$(readlink -f ~/lab/labservice.sh 2>/dev/null || echo '')
case "$PID" in
  ''|*[!0-9]*) echo "进程：PID 文件内容无效（$PID），请先 ./labservice.sh status 排查"; exit 1 ;;
esac
CURDIR=$(readlink -f "/proc/$PID/cwd" 2>/dev/null || echo '')
if [ -n "$SPATH" ] && [ -f "$SPATH" ] && [ "$SPATH" = "$TARGET_SH" ] && [ "$CURDIR" = "$INSTDIR" ] && ps -p "$PID" -o args= 2>/dev/null | grep -q "labservice.sh"; then
  echo "进程：正常（PID=$PID，四要素已核对：路径=目标脚本、cwd=记录目录、命令行=本脚本）"
else
  echo "进程：实例不符或已过期——$PID 不是本场景服务（跨目录同名实例 / PID 复用 / 文件过期），请先 ./labservice.sh status 排查"; exit 1
fi
# 本场景 PID 文件三行（父 PID / 脚本绝对路径 / 启动工作目录）：核对 PID 数字 + 记录路径=目标脚本 + /proc/PID/cwd=记录目录 + 命令行含 labservice.sh，四要素全对齐才认（不用 pgrep -f）；只用它做判断、不做 kill
nc -z localhost 8080 >/dev/null 2>&1 && echo "端口：正常" || echo "端口：不通"
if [ -f "$LOG" ]; then
  [ $(( $(date +%s) - $(stat -c %Y "$LOG") )) -lt 300 ] && echo "日志：5分钟内更新过" || echo "日志：5分钟没动静了"
else
  echo "日志：文件不存在（先确认 LOG 路径和权限）"
fi
# $(( )) = 算术运算（两数相减）；date +%s = 当前秒数；stat -c %Y = 文件最后修改时间（秒）
$ chmod +x health_check.sh && ./health_check.sh

④ 怎么验证做对了：三条中文结论准确反映当前状态。故意杀掉服务再跑一次，结论应变为"挂了/不通/没动静"；把 LOG 改成不存在的路径再跑，应打印"日志：文件不存在"而不是报错——五种情况（不存在/空/坏行/正常/权限不足）都要有明确输出。

A1. labservice.sh（假推理服务，支持 start / stop / status）

⚠️ 附录脚本总警告：脚本内含自动删除命令（rm -f 清 PID 文件、stop 时结束子进程）——全部只作用于练习目录内自己的产物，不会碰其它路径；但仍需遵守：① 只在专用 Ubuntu 虚拟机或可丢弃实验环境运行；② 不把脚本复制到真实服务器使用；③ 每次实验前先 cd ~/lab 并确认 labservice.conf 的 LOGDIR 指向 ~/lab/logs；④ 练完用 ./labservice.sh stop 收尾并复查现场（PID 文件已删、端口已释放）。
#!/bin/bash
# labservice.sh - 练习用假服务，仅在练习目录使用
# 用法：./labservice.sh {start|stop|status}
# PID 文件三行：父进程 PID / 脚本绝对路径 / 启动工作目录 —— 实例唯一标识
# stop 通知父进程，由父进程 trap 负责停子服务并 exit 0
set -u

DIR="$(cd "$(dirname "$0")" && pwd)"
CONF="$DIR/labservice.conf"
PID_FILE="$DIR/labservice.pid"

if [ ! -f "$CONF" ]; then
  echo "配置文件不存在：$CONF"
  exit 1
fi
source "$CONF"
mkdir -p "$LOGDIR" 2>/dev/null
if [ ! -d "$LOGDIR" ] || [ ! -w "$LOGDIR" ]; then
  echo "日志目录不可写：$LOGDIR"
  exit 1
fi
LOG="$LOGDIR/labservice.log"

SRV=""                       # 子服务 PID（全局，供 trap 收尾）

parent_is_ours() {           # 三要素认领：PID 文件记录的实例与本脚本一致
  [ -f "$PID_FILE" ] || return 1
  local pid spath instdir curdir args
  pid=$(sed -n '1p' "$PID_FILE" 2>/dev/null) || return 1
  spath=$(sed -n '2p' "$PID_FILE")
  instdir=$(sed -n '3p' "$PID_FILE")
  # 1) 路径一致：PID 文件是本脚本实例写的（同目录同文件），别的目录实例路径不同
  [ "$spath" = "$(readlink -f "$0")" ] || return 1
  # 2) PID 有效且命令行确实是本脚本
  args=$(ps -p "$pid" -o args= 2>/dev/null || true)
  case "$args" in
    *"labservice.sh"*) : ;;
    *) return 1 ;;
  esac
  # 3) 工作目录一致：PID 复用成别目录同名脚本时，cwd 不同即拒绝
  curdir=$(readlink -f "/proc/$pid/cwd" 2>/dev/null || echo '')
  [ "$curdir" = "$instdir" ] || return 1
  return 0
}

stop_service() {             # 只由父进程的 trap 调用：停子服务、清 PID 文件
  if [ -n "$SRV" ]; then
    kill -TERM "$SRV" 2>/dev/null
    wait "$SRV" 2>/dev/null
    kill -0 "$SRV" 2>/dev/null && kill -KILL "$SRV" 2>/dev/null
  fi
  rm -f "$PID_FILE"
  echo "[$(date '+%F %T')] [INFO] 收尾完成：子服务已停、PID 文件已清理" >> "$LOG" 2>/dev/null || true
}

stop_cmd() {                 # ./labservice.sh stop：通知父进程
  if [ ! -f "$PID_FILE" ]; then
    echo "本场景没有可停止的服务（PID 文件不存在）"
    exit 0
  fi
  if ! parent_is_ours; then
    echo "[拒绝] PID 文件不属于本实例（跨目录同名 / PID 复用 / 文件过期），已停止处理，不影响其他实例"
    exit 1
  fi
  local pid
  pid=$(sed -n '1p' "$PID_FILE")
  echo "发送停止信号给父进程 PID=$pid（由它负责停子服务并清理）"
  kill -TERM "$pid" 2>/dev/null || true
  local i
  for i in $(seq 1 50); do
    if ! kill -0 "$pid" 2>/dev/null && [ ! -f "$PID_FILE" ] && ! ss -tln 2>/dev/null | grep -q ":$PORT "; then
      echo "服务已完全停止（父进程退出、PID 文件已清理、端口已释放）"
      exit 0
    fi
    sleep 0.2
  done
  echo "[警告] 10 秒内未完全停止，请检查：ps -p $pid、ls -l $PID_FILE、ss -tlnp | grep :$PORT"
  exit 1
}

status_cmd() {
  if [ ! -f "$PID_FILE" ]; then echo "状态：未运行"; exit 1; fi
  if ! parent_is_ours; then echo "状态：PID 文件不属于本实例（跨目录同名 / 过期 / PID 复用）"; exit 1; fi
  echo "运行中：父进程 PID=$(sed -n '1p' "$PID_FILE")，端口=$PORT"
  exit 0
}

start_service() {
  if ss -tlnp 2>/dev/null | grep -q ":$PORT "; then
    echo "[ERROR] 端口 $PORT 已被占用：$(ss -tlnp 2>/dev/null | grep ":$PORT ")"
    return 1
  fi
  if parent_is_ours; then
    echo "服务已经运行：父进程 PID=$(sed -n '1p' "$PID_FILE")"
    return 1
  fi
  [ -f "$PID_FILE" ] && rm -f "$PID_FILE"   # 清掉过期残留
  echo "[$(date '+%F %T')] [INFO] 服务启动中，配置端口=$PORT" >> "$LOG"
  trap 'stop_service; exit 0' TERM
  trap 'stop_service; exit 130' INT
  if ! [[ "$PORT" =~ ^[0-9]+$ ]]; then
    echo "[$(date '+%F %T')] [ERROR] 端口配置非法: $PORT（必须是数字）" >> "$LOG"
    return 1
  fi
  python3 -m http.server "$PORT" >/dev/null 2>>"$LOG" &
  SRV=$!
  { echo "$$"; echo "$(readlink -f "$0")"; echo "$DIR"; } > "$PID_FILE"
  sleep 1
  if ! kill -0 "$SRV" 2>/dev/null; then
    echo "[$(date '+%F %T')] [ERROR] 端口 $PORT 监听失败" >> "$LOG"
    rm -f "$PID_FILE"
    return 1
  fi
  echo "[$(date '+%F %T')] [INFO] 服务启动成功，父进程 PID=$$ 子进程 PID=$SRV，端口=$PORT" >> "$LOG"
  while true; do
    echo "[$(date '+%F %T')] [INFO] 服务心跳正常" >> "$LOG"
    # 子服务退出检测：kill -0 对 zombie 仍为真，所以再查进程状态 Z
    if ! kill -0 "$SRV" 2>/dev/null; then
      echo "[$(date '+%F %T')] [ERROR] 子服务已退出，父服务以非 0 退出（供 Restart=on-failure 触发）" >> "$LOG"
      rm -f "$PID_FILE"
      exit 1
    fi
    STAT=$(ps -o stat= -p "$SRV" 2>/dev/null | tr -d ' ')
    case "$STAT" in
      Z*) echo "[$(date '+%F %T')] [ERROR] 子服务已成 zombie（被外部 kill -9），父服务以非 0 退出（供 Restart=on-failure 触发）" >> "$LOG"
          rm -f "$PID_FILE"
          exit 1 ;;
    esac
    sleep 3
  done
}

case "${1:-}" in
  start) start_service ;;
  stop) stop_cmd ;;
  status) status_cmd ;;
  *) echo "用法：$0 {start|stop|status}"; exit 1 ;;
esac

PID 文件三行 = 实例唯一标识：父进程 PID / 脚本绝对路径 / 启动工作目录。stop/status 按"路径一致 + 命令行是本脚本 + 工作目录一致"三要素认领——两个目录各跑同名脚本也不会误认。子服务退出检测：kill -0 + 进程状态 Z（zombie）双查——被外部 kill -9 后即使成为 zombie 也能在下一轮心跳检出 → 父进程 exit 1（供 Restart=on-failure）；正常 stop/systemd TERM → trap 收尾 exit 0。请分别复核：正常 start/status/stop、Ctrl+C、重复 start、异常退出和过期 PID 文件；收尾时确认 PID 文件已删、端口不再监听、练习进程不再存在。

# backup.sh —— 把指定目录打包备份，文件名带日期+时间（不会覆盖旧备份）
# 用法：./backup.sh 要备份的目录（先 chmod +x backup.sh）

  echo "用法：./backup.sh 要备份的目录"
  exit 1

  echo "源目录不存在或不可读：$1"
  exit 1
fi

D2. disk_alert.sh（磁盘超 80% 告警）

#!/bin/bash
# disk_alert.sh —— 磁盘使用率超过 80% 就告警
# 用法：./disk_alert.sh（可放进 crontab 定时跑）
THRESHOLD=80
if ! df / > /dev/null 2>&1; then
  echo "df 执行失败（路径不存在或环境异常），退出"
  exit 1
fi
USE=$(df / | tail -1 | awk '{print $5}' | tr -d '%')
if [ "$USE" = "" ]; then
  echo "解析不到使用率（df 输出异常），退出"
  exit 1
fi
if ! [ "$USE" -eq "$USE" ] 2>/dev/null; then
  echo "使用率不是数字（$USE），退出"
  exit 1
fi
if [ "$USE" -gt "$THRESHOLD" ]; then
  echo "磁盘告警：根分区使用率 $USE%，超过 $THRESHOLD%"
else
  echo "磁盘正常：根分区使用率 $USE%"
fi

逐行要点：取数 → 判断 → 行动的巡检三步曲；df / 看根分区（第 7 章）、tail -1 取最后一行（第 3 章）、awk '{print $5}' 取第 5 列即使用率（第 4 章）、tr -d '%' 删掉百分号只剩数字（tr=字符转换、-d=删除，第 13 章 13.2）、$(...) 把命令输出装进变量（第 13 章）、-gt 在 [ ] 里表示"大于"（第 13 章）。三层防护：① df 本身失败先退出（路径不存在/环境异常）；② 解析结果为空先退出；③ [ "$USE" -eq "$USE" ] 是"数值自比较"技巧——USE 不是纯数字时 test 会失败（非 0），! 翻转后进分支退出，防止把垃圾当数字比大小。阈值放变量，以后想改只改一行。验证：正常时打印"磁盘正常：X%"；把 THRESHOLD 改成 0 再跑，应打印"磁盘告警"；把 df / 换成 df /nonexist 再跑，应打印"df 执行失败"且退出码 1——三种分支都出现即正确；建议配 crontab 每天跑一次（第 13 章）。

D3. service_guard.sh（服务挂了自动拉起）

#!/bin/bash
# service_guard.sh —— 服务挂了自动拉起（失败必须返回非 0，不伪装成功）
# 用法：./service_guard.sh 服务名（如 ssh、nginx）
if [ "$1" = "" ]; then
  echo "用法：./service_guard.sh 服务名"
  exit 1
fi
if systemctl is-active --quiet "$1" 2>/dev/null; then
  echo "$1 运行中，无需处理"
  exit 0
fi
echo "$1 没在运行，尝试拉起..."
if ! sudo systemctl start "$1" 2>/dev/null; then
  echo "$1 启动命令失败（服务不存在 / 配置错误 / systemd 不可用），看日志：journalctl -u $1"
  exit 1
fi
if systemctl is-active --quiet "$1"; then
  echo "$1 已拉起"
  exit 0
else
  echo "$1 拉起后仍不在运行（active/failed/offline 状态不同，逐一核实），看日志：journalctl -u $1"
  exit 1
fi

逐行要点：保活三段——查（is-active 问"还活着吗"）→ 拉（死了就 start）→ 复核（拉完再问一次，没起来就看日志）。systemctl is-active 专门问服务状态，--quiet 安静模式只通过退出码回答（0=在，非 0=不在），正好放进 if（第 10 章）；sudo systemctl start 拉起需管理员权限（第 10 章）；journalctl -u 看该服务日志（第 10 章）。返回码纪律：成功（本来就在 / 拉起成功）返回 0；启动命令失败、拉起后仍 inactive/failed 都返回 1——失败不伪装成功，方便定时任务据此告警。2>/dev/null 把 systemd 不可用时的报错吞掉（第 4 章重定向），由退出码分支统一处理。验证：./service_guard.sh ssh 输出"运行中"、退出码 0；先 sudo systemctl stop ssh 再跑，应看到"没在运行 → 尝试拉起 → 已拉起"、退出码 0；对一个不存在的服务名跑，应打印"启动命令失败"、退出码 1（🌐 需电脑 Ubuntu；systemd 不可用的容器/WSL 记为环境限制）。
