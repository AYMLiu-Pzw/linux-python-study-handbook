开始之前 · 先弄懂这是什么（2 分钟）

① 是什么：Docker 是把程序和它需要的一切（依赖、配置）打成一个包的工具 —— 这个包叫"镜像"，跑起来的实例叫"容器"。生活类比：像搬家的标准集装箱——家具（程序）和说明书（依赖）一起装进标准箱子，换任何一条船（任何服务器）都能直接搬下来用。

② 干什么用：专治"在我机器上能跑、到你机器上就报错"。同一镜像在哪跑都一样；AI 运维把推理服务、监控组件打包成容器后，一条 docker compose up -d 就能起一整套。

③ 为什么要学（＋实战里怎么用）：“容器和虚拟机有什么区别”“Dockerfile 写过吗”——实战里都会碰到；不容器化，服务就没法可靠交付。

④ 长什么样 / 怎么用：最小三步：写 Dockerfile → docker build -t app .（做箱子）→ docker run -p 8080:80 app（搬出来跑）。本册从 4-00（先懂 YAML）走到 4-10，最后把你自己的脚本容器化。

4-00 前置：YAML 是什么（15 分钟）

时长：休息日 15 分 ｜ 工作日 15 分　｜　前置：无　｜　状态：已写（第二轮）

为什么先学它：Docker Compose 和 K8s 的配置文件都是 YAML。不会读它，后面那两条命令你写不出来。

三句话说完：① 缩进 = 层级（用空格，别用 Tab）；② 冒号 = 键和值；③ 一行以 - 开头 = 列表里的一项。

services:            # 顶层的键
  web:               # 缩进 2 格：web 是 services 里的一项
    image: nginx     # 冒号左边是键，右边是值
    ports:
      - "8080:80"    # 前面带 - ：这是列表里的一项

怎么读：像读目录树——缩进越深，层级越里；冒号左边是名字，右边是内容。

三个坑：① 用 Tab 缩进会直接报错（YAML 只认空格）；② 冒号后面必须有一个空格；③ 同一个键不能出现两次，后面的会盖掉前面的。

实战价值：真正让你现场改一段 compose 文件时，你不会因为缩进错一格就卡住。

开始之前 · 先把镜像加速器配好（只做一次，约 10 分钟）

为什么放在这里：下一步（4-01）你就要 docker pull 了。国内直连 Docker Hub 大概率超时，先把这一步做掉，后面 4-01、4-02、08 册的监控三件套、09 册的 K8s 才拉得动镜像。

不配会看到什么（真实报错样式）：

$ docker pull hello-world
Error response from daemon: Get "https://registry-1.docker.io/v2/": dial tcp 154.83.15.45:443: i/o timeout

看到 i/o timeout 就说明是"连不上仓库"，不是你的命令写错了。

三步配好（可直接复制）

$ sudo mkdir -p /etc/docker
$ sudo tee /etc/docker/daemon.json >/dev/null <<'EOF'
{
  "registry-mirrors": [
    "https://docker.m.daocloud.io",
    "https://docker.1ms.run",
    "https://docker.1panel.live"
  ]
}
EOF
$ sudo systemctl restart docker
$ docker info | grep -A3 "Registry Mirrors"
 Registry Mirrors:
  https://docker.m.daocloud.io/
  https://docker.1ms.run/
  https://docker.1panel.live/

解读：daemon.json 是 Docker 的配置文件；registry-mirrors 就是"镜像加速器名单"——拉镜像时 Docker 先问这几个国内站点，不再直连国外。看到 Registry Mirrors 下面列出这三个地址，就算配好了。

验证一次

$ docker run hello-world
Hello from Docker!
This message shows that your installation appears to be working correctly.

（注意区别：docker pull 只把镜像拉下来，输出是 Using default tag / Pulling from / Digest / Status: Downloaded… 这种状态行；让它"跑出那几行字"的是 docker run。）

三个坑：① JSON 里不能写注释，最后一个地址后面不能多逗号（多一个逗号 Docker 会起不来）；② 改完必须 sudo systemctl restart docker 才生效；③ 三个加速器是轮着试的，某个哪天挂了，把顺序调一下换一个即可。

三个都不行时（兜底）：① 换阿里云容器镜像服务的个人专属加速地址——登录阿里云 → 容器镜像服务（ACR）→「镜像加速器」页免费领取，按页面说明配置；② 或临时直连重试——docker pull 卡住就换个网络、或过一会儿再试；自检：docker info 的 Registry Mirrors 里是不是你配的那几个（改完没 systemctl restart docker 的话，这里还是旧值）。

只做一次。以后重装系统或换机器时，回来再做一遍。

4-01 镜像与容器是什么：跑起第一个容器

时长：休息日 2.5 小时 ｜ 工作日 15 分（只做第 1、2 步）　｜　前置：4-00

这一关只解决一件事：分清"镜像"和"容器"，并且亲手跑起来一个。

一个比喻：镜像 = 菜谱（只读的模板，放在仓库里）；容器 = 照着菜谱做出来的那盘菜（能跑、能停、能删，删了菜谱还在）。同一份菜谱可以同时做出好几盘菜（这就是"一个镜像起多个容器"）。

步骤 1：确认 Docker 装好了

$ docker --version
Docker version 27.3.1, build ce12230   # 示例（本册输出按 Docker 27 录）；26.04 源里现在是 29.x（以你机器为准）

版本差怎么读：26.04 的 docker.io 是 29.x——docker images 的列变成 IMAGE / ID / DISK USAGE / CONTENT SIZE / EXTRA，docker ps / docker port 可能多出 IPv6 行，docker build 会走经典构建器（Step 1/4 …）。看结构就行，不影响判定。

解读：有版本号就是装好了。没装的话用 sudo apt install -y docker.io（Ubuntu 源里就有；再装上 compose 插件：sudo apt install -y docker-compose-v2，否则后面 4-07 起会报 docker: unknown command: docker compose）。

不管是刚装的还是早就装好的，用 Docker 前先把自己加进 docker 组：sudo usermod -aG docker $USER → 退出重登一次（WSL 里关掉终端重开即可）。不加这一步，docker 命令会报 permission denied ... /var/run/docker.sock——这是新手的一号卡点。

步骤 2：跑第一个容器

$ docker run hello-world

Hello from Docker!
This message shows that your installation appears to be working correctly.
...

解读：docker run 一共干了两件事——先从仓库把镜像拉下来（本地没有 hello-world 这个镜像），再照着它起一个容器跑出那几行字。容器跑完就退出了，镜像还留在你机器上。这就是"镜像和容器不是一回事"。

步骤 3：看清"镜像留下、容器退出"

$ docker images
REPOSITORY    TAG       IMAGE ID       CREATED       SIZE
hello-world   latest    ee301c921b8a   5 months ago  9.14kB

$ docker ps -a
CONTAINER ID   IMAGE         COMMAND    CREATED          STATUS                     NAMES
9c5b1e2a77f1   hello-world   "/hello"   10 seconds ago   Exited (0) 9 seconds ago   happy_allen

解读：docker images 列的是镜像（模板，只有一份）；docker ps -a 列的是容器（跑过的实例，STATUS 那列写着 Exited (0) = 正常退出，退出码 0）。-a 表示连已经退出的也一起看；不加 -a 只看正在跑的。

完成判定

□ 能用自己的话说清镜像和容器的区别　□ docker run hello-world 能跑出输出　□ 能说出 docker images 和 docker ps -a 各看的是什么　□ 能解释 STATUS 里的 Exited (0) 是什么意思

实验闭环：先记录原状态 → 操作 → 按输出 / 退出码验证 → 恢复现场。

回滚方式：实验完把容器清掉即可——docker rm happy_allen（把 NAMES 换成你自己那行）；镜像想删就 docker rmi hello-world。删了都不影响系统。

踩坑记录位：现象 → 原因 → 解决 → 一句话总结（留空自己填）

实战价值：这是关于容器最经典的一问——"容器和虚拟机/镜像有什么区别"，你现在有一手的说法。

4-02 六件套：pull / run / ps / logs / exec / stop·rm

时长：休息日 2.5 小时 ｜ 工作日 15 分（每天敲一条，边敲边背）　｜　前置：4-01

这一关是：容器日常操作的六组命令（六节、七个命令名，最后一节 stop 和 rm 一起讲）。每条都按"输入 → 输出 → 解读"写，你照着敲一遍就算过。

① pull：先把镜像拿下来

$ docker pull nginx:alpine
alpine: Pulling from library/nginx
...
Status: Downloaded newer image for nginx:alpine

解读：nginx:alpine 里的冒号后面是标签（版本）；alpine 是一个特别小的 Linux 发行版，用它做出来的镜像只有几十 MB。不写标签默认是 latest。

② run：起容器（最常用的两条参数）

$ docker run -d --name web -p 8080:80 nginx:alpine
7f3a9c1d2e4b8a6f0c5d3e2b1a9f8c7d6e5b4a3c2d1e0f9a8b7c6d5e4f3a2b1c

解读：-d = 后台跑（不占着你的终端）；--name web = 给容器起个名字（方便后面 stop/rm 时不用抄那串乱码 ID）；-p 8080:80 = 把本机 8080 接到容器 80（下一关细讲）；最后的 nginx:alpine 是"用哪个镜像"。输出那一长串就是容器 ID。

③ ps：看现在有哪些容器

$ docker ps
CONTAINER ID   IMAGE          COMMAND                  STATUS         PORTS                  NAMES
7f3a9c1d2e4b   nginx:alpine   "/docker-entrypoint.…"   Up 12 seconds  0.0.0.0:8080->80/tcp   web

解读：STATUS 是 Up 就说明它在跑；PORTS 那列 0.0.0.0:8080->80/tcp 就是把本机 8080 转进容器 80 的证据。这时候你浏览器打开 http://localhost:8080 就能看到 nginx 欢迎页——这就是"服务跑起来了"。（刚 run 的一两秒里页面可能还没就绪——nginx 在容器里启动要一点时间，稍等/刷新一下；docker logs web 里看到 "start worker processes" 就是稳了。）

④ logs：容器里的程序说了什么

$ docker logs web
/docker-entrypoint.sh: Configuration complete; ready for start up
2026/10/09 12:03:11 [notice] 1#1: start worker processes

解读：容器里的程序输出不会留在你的终端里，要用 logs 捞出来——排障第一步永远是看日志。加 -f 就是实时盯（和 Linux 的 tail -f 一个意思）。

⑤ exec：进容器里面看

$ docker exec -it web sh
/ # ls /etc/nginx
conf.d          mime.types      nginx.conf   # 示例：条目数随 nginx 版本
/ # exit

解读：-it = 交互式终端（i 是标准输入，t 是终端）；sh 是要执行的命令（alpine 里没有 bash，用 sh）。进容器只为了看和查，改完的东西容器一删就没了（这也是实战里常问的点）。

⑥ stop / rm：停掉、删掉

$ docker stop web && docker rm web
web
web

解读：stop 是温柔地停（先发 TERM，和你在 Linux 里学的优雅停机一个道理），rm 才是删掉容器。容器不删会一直占着名字和端口，所以练习完记得清理。

完成判定

□ 四个字：上面六节里的命令各自能不看笔记敲一遍　□ 能说出 -d、--name、-p 各解决什么问题　□ 能说出 logs 和 exec 分别什么时候用　□ 练习完把容器清干净（docker ps -a 里没有遗留）

实验闭环：先记录原状态 → 操作 → 按输出 / 退出码验证 → 恢复现场。

回滚方式：docker stop + docker rm 一删就回到原样；镜像用 docker rmi nginx:alpine 删（不吃磁盘时不用删）。

踩坑记录位：现象 → 原因 → 解决 → 一句话总结（留空自己填）

实战价值：工作里常问"容器起不来你怎么查"，答案就是这个顺序——ps（是不是 Up）→ logs（报什么错）→ exec（进去看现场）。

4-03 数据卷与端口映射

时长：休息日 2.5 小时 ｜ 工作日 15 分　｜　前置：4-02

这一关解决两个"为什么"：为什么容器里的数据一删就没？为什么外面连不上容器里的服务？

一、先把"数据会消失"亲眼看一遍

$ docker run -it --name tmp ubuntu:26.04 bash
root@5a1b2c3d4e5f:/# echo "hello" > /data.txt && cat /data.txt
hello
root@5a1b2c3d4e5f:/# exit

$ docker rm tmp && docker run -it --name tmp2 ubuntu:26.04 bash
root@9f8e7d6c5b4a:/# cat /data.txt
cat: /data.txt: No such file or directory

解读：容器是"一次性的盘子"——删掉容器，写在容器里的东西全没了，因为那些写入只存在于容器那一层可写层里。想留下，就得把数据放到容器外面。

二、数据卷 -v：把本机目录接进容器

$ mkdir -p ~/lab/docker-data && echo "我在外面写的" > ~/lab/docker-data/note.txt
$ docker run --rm -it -v ~/lab/docker-data:/data ubuntu:26.04 bash
root@a1b2c3d4e5f6:/# cat /data/note.txt
我在外面写的
root@a1b2c3d4e5f6:/# echo "我在容器里写的" >> /data/note.txt && exit

$ cat ~/lab/docker-data/note.txt
我在外面写的
我在容器里写的

解读：-v 本机路径:容器路径 = 把本机的目录"接"到容器里。两边看到的是同一份文件：容器里改的，外面立刻能看到。这样容器删了，数据还在（因为文件本来就住在你机器上）。--rm 表示容器退出后自动删掉。

一句话记住：无状态的放容器里，有状态的（数据、日志、配置）挂出来。

三、端口映射 -p：让外面能连进来

$ docker run -d --name web -p 8080:80 nginx:alpine
$ curl -s -o /dev/null -w "%{http_code}\n" http://localhost:8080
200
$ docker port web
80/tcp -> 0.0.0.0:8080

解读：容器有自己的"内网"（里面 80 端口在听），外面默认连不上。-p 8080:80 = 本机 8080 → 容器 80（前面是本机，后面是容器，别写反）。curl 返回 200 就说明通了——这也是你以后验证"服务有没有起来"的标准动作。

完成判定

□ 能说出"为什么容器删了数据就没了"，并演示一次数据卷保住数据　□ 能自己起一个 nginx 并用 curl 验证 200　□ 能说出 -p 8080:80 里前后两个数字各是什么　□ 能说出什么该挂卷、什么不用

实验闭环：先记录原状态 → 操作 → 按输出 / 退出码验证 → 恢复现场。

回滚方式：实验容器 docker rm -f 掉；挂载目录在 ~/lab 里，删掉不影响系统。

踩坑记录位：现象 → 原因 → 解决 → 一句话总结（留空自己填）

实战价值："容器里的数据怎么持久化""为什么 8080 能访问、80 不行"——这两问几乎每次用容器都会碰到。

4-04 写第一个 Dockerfile

时长：休息日 2.5 小时 ｜ 工作日 15 分　｜　前置：4-03

Dockerfile 是什么：一份"怎么把东西装进镜像"的说明书，五行就能跑通。你只要先记住这五个指令，别的等用到再查。

指令干什么一句话理解
FROM选基础镜像（从哪个系统开始搭）打地基，永远写第一行
RUN在构建时执行命令（装软件、建目录）装修：装的时候做一次
COPY把本机文件复制进镜像把你的脚本搬进去
EXPOSE声明容器里要听哪个端口（给读的人看的说明）留个纸条：我用 80
CMD容器启动时默认执行的那条命令开火：跑起来时做

动手：写一个自己的 hello 镜像

$ mkdir -p ~/lab/myimage && cd ~/lab/myimage
$ cat > Dockerfile <<'EOF'
FROM ubuntu:26.04
RUN apt-get update && apt-get install -y curl
COPY hello.sh /hello.sh
RUN chmod +x /hello.sh
CMD ["/hello.sh"]
EOF
$ cat > hello.sh <<'EOF'
#!/bin/bash
echo "容器里跑起来了，里面装的是："
curl --version | head -1
EOF

构建并运行

$ docker build -t my-hello:1.0 .
[+] Building 12.4s
 => [1/4] FROM docker.io/library/ubuntu:26.04
 => [2/4] RUN apt-get update && apt-get install -y curl
 => [3/4] COPY hello.sh /hello.sh
 => [4/4] RUN chmod +x /hello.sh
 => => naming to docker.io/library/my-hello:1.0

$ docker run --rm my-hello:1.0
容器里跑起来了，里面装的是：
curl 8.5.0 (x86_64-pc-linux-gnu)  # 示例（版本号随机器）；脚本里 head -1 只取了第一行，完整输出还有一大串特性开关

解读：docker build -t 名字:版本 . 里的最后那个点不能少——它表示"用当前目录里的 Dockerfile"。build 的过程就是一行一行照着 Dockerfile 做，所以输出里能看到 [1/4]、[2/4]……每一步都生成一层。

为什么 COPY 要放在装软件之后：Docker 有缓存，哪一层变了，它和它后面的层才重建。你改脚本的时候不想重装一遍 curl，所以"变化少的放前面、变化多的放后面"。

完成判定

□ 能不看笔记写出 FROM / RUN / COPY / CMD 四行　□ 能说清 RUN 和 CMD 的区别（构建时 vs 启动时）　□ 能说清 build 命令最后那个点是什么　□ 能说出 COPY 为什么要放在后面

实验闭环：先记录原状态 → 操作 → 按输出 / 退出码验证 → 恢复现场。

回滚方式：练废的镜像 docker rmi my-hello:1.0 删掉重来；~/lab/myimage 里的文件随时可改。

踩坑记录位：现象 → 原因 → 解决 → 一句话总结（留空自己填）

实战价值："你们的镜像怎么构建的？"——能讲清"分层 + 缓存 + 变化多的放后面"，比背十条指令管用。

4-05 把自己的脚本打包成镜像跑起来

时长：休息日 2.5 小时 ｜ 工作日 15 分　｜　前置：4-04 ｜ 原料：阶段 2 的 disk_alert.sh 或 backup.sh

这一关的意义：从"会跑别人的镜像"变成"能把自己的东西装进镜像"。这也是阶段 4 检查点的前置动作。

步骤 1：把脚本准备好

$ mkdir -p ~/lab/docker-scripts && cd ~/lab/docker-scripts
$ cp ~/lab/shell-scripts/disk_alert.sh .    # 换成你自己的脚本路径
$ cat disk_alert.sh
#!/bin/bash
THRESHOLD=80
USE=$(df -h / | awk 'NR==2 {print $5}' | tr -d '%')
if [ "$USE" -ge "$THRESHOLD" ]; then
  echo "[告警] 磁盘使用率 ${USE}%，超过阈值 ${THRESHOLD}%"
else
  echo "[正常] 磁盘使用率 ${USE}%"
fi

步骤 2：写 Dockerfile

FROM ubuntu:26.04
RUN apt-get update && apt-get install -y bash coreutils && rm -rf /var/lib/apt/lists/*
WORKDIR /opt/scripts
COPY disk_alert.sh ./disk_alert.sh
RUN chmod +x disk_alert.sh
CMD ["./disk_alert.sh"]

解读：WORKDIR = 进容器后默认站在哪个目录（省得每句都写绝对路径）；rm -rf /var/lib/apt/lists/* 是装完就删缓存，让镜像小一点；CMD 用方括号写法（推荐，避免 shell 解析带来的怪问题）。

步骤 3：构建、运行、验证

$ docker build -t disk-alert:1.0 .
$ docker run --rm disk-alert:1.0
[正常] 磁盘使用率 42%      # 示例数值，随你机器

$ docker run --rm -e THRESHOLD=10 disk-alert:1.0
[正常] 磁盘使用率 42%

解读：脚本在容器里跑通了。注意后一条：我们想试试改阈值，但脚本里阈值是写死的（THRESHOLD=80），所以在外面改环境变量没用。这就是"参数要能传进去"的意义——顺手把脚本改成从环境变量读阈值：

版本差异说明：本节贴的"写死版"是为了展示"参数要能传进去"的演进；你阶段 2 交付的 disk_alert.sh（03 册附录 D2）本来就是 THRESHOLD=${THRESHOLD:-80} 环境变量版——如果手头就是那份，可以跳过这步改写，直接 build 后用 -e 传值验证。

THRESHOLD=${THRESHOLD:-80}     # 有传就用传进来的，没传默认 80

改完重新 build 再跑，换一个一定会触发的值就能看到告警：docker run --rm -e THRESHOLD=0 disk-alert:1.0（或填一个低于你机器当前磁盘使用率的值）——用 10 这类值在自己机器上可能根本不触发，那是"阈值没到"，不是"没生效"。这一步做出来，你就完成了"脚本 → 镜像 → 可配置服务"的升级。

完成判定

□ 自己的脚本能在容器里跑出结果　□ 能说出 WORKDIR 解决了什么问题　□ 改一处脚本后重新 build，能说清"哪几层用了缓存"　□ 用 -e 把阈值传进去并触发一次告警

4-06 镜像瘦身与分层

时长：休息日 2.5 小时 ｜ 工作日 15 分　｜　前置：4-05　｜　状态：已写（第三轮）

这一关只解决一件事：让你的镜像不要又大又慢。你要是只会写 Dockerfile，镜像是能跑，但别人问"你这镜像多大、为什么这么大"，就答不上来了。

步骤 1：先看看镜像是怎么做出来的

$ docker history my-hello:1.0
IMAGE          CREATED BY                                      SIZE
9f8e7d6c5b4a   CMD ["/hello.sh"]                               0B
1a2b3c4d5e6f   RUN chmod +x /hello.sh                          0B
2b3c4d5e6f70   COPY hello.sh /hello.sh                         121B
3c4d5e6f7081   RUN apt-get update && apt-get install -y curl   92MB
4d5e6f708192   /bin/sh -c #(nop)  FROM ubuntu:26.04           78MB

解读：Dockerfile 里每一条指令就是一层，从下往上看就是构建顺序。装 curl 那一条一口气吃掉 92MB —— 因为 apt 装的包加上缓存全留在这一层里了。

步骤 2：把体积压回去

FROM ubuntu:26.04
RUN apt-get update && apt-get install -y curl \
    && rm -rf /var/lib/apt/lists/*          # ← 装完在同一层里删缓存
COPY hello.sh /hello.sh
RUN chmod +x /hello.sh
CMD ["/hello.sh"]
$ docker build -t my-hello:1.1 . && docker images | head -3
REPOSITORY   TAG   IMAGE ID       SIZE
my-hello     1.1   7a8b9c0d1e2f   96MB
my-hello     1.0   9f8e7d6c5b4a   170MB

解读：170MB → 96MB。关键动作只有一个："装东西"和"清缓存"要写在同一层里（用 && 连起来）。分成两条 RUN，中间那层已经把缓存固化下来了，后面删也没用。

步骤 3：缓存与顺序（这一条实战里常问）

$ docker build -t my-hello:1.2 .      # 什么都没改
 => CACHED [2/4] RUN apt-get update && apt-get install -y curl ...
 => CACHED [3/4] COPY hello.sh /hello.sh
# 改一行 hello.sh 再 build：
 => CACHED [2/4] RUN apt-get update ...        ← 没重装 curl
 => [3/4] COPY hello.sh /hello.sh              ← 从这层开始重做

解读：哪一层变了，它和它后面的层才重建。"很少变的东西放前面，经常变的东西放后面" 就是这个道理（所以装依赖在 COPY 代码之前）。

延伸（点到为止）：多阶段构建

FROM golang:1.23 AS builder     # 第一阶段：编译用的"工地"
WORKDIR /src
COPY main.go .
RUN go build -o app main.go

FROM alpine:3.20                # 第二阶段：只把成品搬进小房子
COPY --from=builder /src/app /app
CMD ["/app"]

解读：把"编译要的一大堆工具"留在第一阶段，最终镜像里只放能跑的成品。名字记住就行，等他真遇到编译型语言再看细节。

完成判定

□ 能用 docker history 说出哪一层最大　□ 把"装 + 清缓存"写进同一层后，镜像确实变小　□ 能说出为什么 COPY 要放在装依赖之后　□ 能说出多阶段构建解决了什么问题（一句话）

实验闭环：先记录原状态 → 操作 → 按输出 / 退出码验证 → 恢复现场。

回滚方式：旧镜像 docker rmi my-hello:1.0 删掉即可；Dockerfile 改坏了就从 ~/lab/myimage 里的备份恢复。

踩坑记录位：现象 → 原因 → 解决 → 一句话总结（留空自己填）

实战价值："你们镜像怎么优化"——答"装和清缓存写同一层、变化少的放前面、必要时多阶段构建"，这三句就够了。

4-07 docker compose 起两个服务

时长：休息日 3 小时 ｜ 工作日 15 分　｜　前置：4-00（YAML）＋ 4-02　｜　状态：已写（第三轮）

为什么需要 compose：一条 docker run 只能起一个容器。真实场景动辄"应用 + 缓存 + 数据库"三四个容器，一个个手敲容易漏参数。compose 就是把这些 docker run 写成一份文件，一声令下全起来。

步骤 1：写文件

$ mkdir -p ~/lab/two-services && cd ~/lab/two-services
$ cat > docker-compose.yml <<'EOF'
services:
  web:
    image: nginx:alpine
    container_name: web
    ports:
      - "8080:80"
    depends_on:
      - cache
    restart: unless-stopped

  cache:
    image: redis:7-alpine
    container_name: cache
    restart: unless-stopped
EOF

解读：这份文件就是两个 docker run 的"清单版"。注意 services: 下缩进的两格才是服务名（YAML 的缩进就是层级，4-00 学过）。depends_on 表示"起 web 之前先起 cache"。

步骤 2：起来

$ docker compose up -d
[+] Running 3/3
 ✔ Network two-services_default   Created
 ✔ Container cache                Started
 ✔ Container web                  Started

$ docker compose ps
NAME    IMAGE              STATUS         PORTS
cache   redis:7-alpine     Up 10 seconds  6379/tcp
web     nginx:alpine       Up 10 seconds  0.0.0.0:8080->80/tcp

解读：两个都是 Up 才算成功。compose 还顺带建了一个网络（two-services_default），下一关讲它。-d 还是"后台跑"的意思。

步骤 3：验证两个服务真的在

$ curl -s -o /dev/null -w "%{http_code}\n" http://localhost:8080
200
$ docker compose exec cache redis-cli ping
PONG
$ docker compose logs web | tail -2
2026/10/09 12:30:01 [notice] 1#1: start worker process 29

解读：200 = web 活着，PONG = cache 活着。注意命令从 docker exec 变成了 docker compose exec 服务名 —— 用服务名就不用抄容器 ID 了。

步骤 4：收工

$ docker compose down
[+] Running 3/3
 ✔ Container web    Removed
 ✔ Container cache  Removed
 ✔ Network two-services_default  Removed

解读：down 一条命令把容器和网络都清掉（但具名卷不会删，这是有意的：数据别跟着容器一起消失）。

完成判定

□ 能不看笔记写出一个两服务的 compose 文件　□ up -d / ps / logs / exec / down 五条命令能跑通　□ 能用 curl 200 和 redis PONG 各验证一次　□ 能说出 down 之后什么被删了、什么没被删

实验闭环：先记录原状态 → 操作 → 按输出 / 退出码验证 → 恢复现场。

回滚方式：docker compose down；想连数据卷一起清就 down -v（练习环境随便清，生产环境别乱加 -v）。

踩坑记录位：现象 → 原因 → 解决 → 一句话总结（留空自己填）

实战价值：这是"用 compose 起过多个服务"的实物；后面追问"服务之间怎么找到对方"就接下一关。

4-08 Compose 的网络与依赖顺序

时长：休息日 2.5 小时 ｜ 工作日 15 分　｜　前置：4-07　｜　状态：已写（第三轮）

一、服务之间靠"名字"互相找到

$ cd ~/lab/two-services && docker compose up -d
$ docker compose exec web ping -c 2 cache
PING cache (172.20.0.3): 56 data bytes
64 bytes from 172.20.0.3: seq=0 ttl=64 time=0.071 ms

$ docker compose exec web ping -c 1 baidu.com
ping: bad address 'baidu.com'          # ← 如果这里显示的是 IP（能解析），说明容器用的是宿主机 DNS，正常；解析不通再查 daemon 的 DNS 配置

解读：compose 给这组服务建了一个专属网络，并在里面做了 DNS：服务名（web / cache）就是主机名。所以代码里连 Redis 就写 redis://cache:6379，而不是 localhost——对 web 容器来说，localhost 是它自己。

这就是 5-02 里 Prometheus 要写 node-exporter:9100 的同一个道理。

二、depends_on 不等于"对方已经准备好了"

# 现象：web 启动了，但连不上 redis，报连接被拒
$ docker compose logs web | grep -i "connection" | head -2
 Connection refused (cache:6379)

# 原因：depends_on 只管"先启动 cache 容器"，
#       不代表 redis 进程已经能接受连接（它可能还在加载数据）

解读：depends_on 保证的是启动顺序，不是就绪状态。这是实战里的经典坑。两种正经解法：

# 解法 A（推荐）：应用侧重试 —— 连不上就等 2 秒再试，最多 10 次
# 解法 B：给 cache 加健康检查，web 等它"健康"再起
services:
  cache:
    image: redis:7-alpine
    healthcheck:
      test: ["CMD", "redis-cli", "ping"]
      interval: 5s
      retries: 5
  web:
    image: nginx:alpine
    depends_on:
      cache:
        condition: service_healthy     # ← 等它健康，而不是"启动了"

解读：解法 A 更常用（应用自己扛住"依赖没就绪"），解法 B 更漂亮但只有 compose 支持。两个都记住，够用了。

三、看一眼网络长什么样

$ docker network ls | grep two
8f1c2d3e4f5a   two-services_default   bridge    local
$ docker network inspect two-services_default --format '{{range .Containers}}{{.Name}} {{end}}'
web cache

解读：同一个 compose 项目里的服务自动进同一个 bridge 网络，不同项目之间默认互相看不见（这也是隔离）。

完成判定

□ 能说出为什么代码里写 cache:6379 而不是 localhost:6379　□ 能说出 depends_on 保证了什么、没保证什么　□ 能用两种解法之一演示"依赖没就绪时不崩"　□ 能用 docker network inspect 说出哪个网络里有哪几个容器

实验闭环：先记录原状态 → 操作 → 按输出 / 退出码验证 → 恢复现场。

回滚方式：docker compose down；实验用的网络会跟着一起删。

踩坑记录位：现象 → 原因 → 解决 → 一句话总结（留空自己填）

实战价值："容器里连数据库为什么不用 localhost""depends_on 靠谱吗"——这两个问题答对，就说明你真部署过，不是只看过教程。

4-09 容器排障：日志 / 退出码 / 端口被占

时长：休息日 2.5 小时 ｜ 工作日 15 分　｜　前置：4-02 ＋ 4-07　｜　状态：已写（第三轮）

这一关是阶段 4 的重点：容器起不来时，你要能在 3 分钟内说清"是哪一类问题"。下面三条是排查链，不是命令清单 —— 每一条都是"现象 → 命令 → 判读 → 下一步"。

排查链 ①：容器起不来，先看日志

$ docker compose up -d          # 结果 web 没稳住
[+] Running 2/2
 ✔ Container cache  Started
 ✔ Container web    Started          ← 注意：这里不是 Error

$ docker compose ps             # ← 先看状态：Restarting = 起来又自己退了
web   …   Restarting (1) 3 seconds ago

$ docker compose logs web      # ← 第一步永远是日志
web  | nginx: [emerg] invalid number of arguments in "listen" directive in /etc/nginx/conf.d/default.conf:3

判读："Started" 不等于跑住了——4-07 的 compose 配了 restart: unless-stopped，容器退出后会被自动拉起，所以看不到 Error，而是 Restarting 循环；日志直接告诉你是配置写错（nginx 的 listen 少写了端口）。
下一步：改配置 → docker compose up -d 重来。"Started" 或 "Restarting" 时都先 docker compose ps 看状态、再看日志。若日志是空的，走第 ② 条。

排查链 ②：日志空的，就看退出码

$ docker ps -a | grep web
7f3a9c1d2e4b   web   nginx:alpine   Exited (1) 2 minutes ago

$ docker inspect web --format '{{.State.ExitCode}} {{.State.OOMKilled}}'
1 false
退出码常见含义下一步看哪
0正常结束（一次性任务的正常态）不是故障，看它该不该一直跑
1应用自己报错退出日志；检查配置 / 依赖 / 参数
137被 SIGKILL 杀掉，最常见是内存超限被 OOMdocker inspect 看 OOMKilled；加大内存或查内存泄漏
143进程自己处理 SIGTERM 后主动退出（128＋15；不是所有 docker stop 都是 143）看应用怎么处理 SIGTERM：优雅退出＝0 / 被强杀＝137

判读：137 ＋ OOMKilled: true = 内存超限被 OOM；137 但没 OOM = 被 SIGKILL（最常见就是 docker stop 发了 SIGTERM、等 10 秒没停住，然后强杀），0 = 应用处理 SIGTERM 后优雅退出。
实测（三组，可自己复现）：docker stop 一个 alpine sleep 300 → 137（等满 10 秒后强杀）；docker stop 一个 nginx:alpine → 0（1 秒内优雅退出；前提是让它先跑起来再停——刚 run 就秒停会得到 137，那是没来得及处理信号）；docker kill → 137。所以别背「stop 就是 143」——要看应用怎么处理 SIGTERM。

日志里还有一类"没见过"的报错：exec format error——意思是"可执行文件格式不对"。容器里最常见两因：① 脚本第一行 shebang 缺失或写错（如漏了 #!/bin/bash）；② 文件在 Windows 里编辑过、带了 CRLF 换行。修法：head -1 看第一行、对齐换行符，再 chmod +x 后重新 build 跑。

排查链 ③：容器在跑，但外面连不上（端口被占）

$ docker compose up -d
docker: Error response from daemon: failed to set up container networking: driver failed
programming external connectivity on endpoint web2 (…): Bind for 0.0.0.0:8080 failed: port is already allocated

$ ss -tulnp | grep 8080        # ← 谁占了 8080
tcp   LISTEN 0 511  0.0.0.0:8080  0.0.0.0:*  users:(("nginx",pid=2211,fd=6))

$ docker ps --format '{{.Names}}\t{{.Ports}}' | grep 8080
old-nginx   0.0.0.0:8080->80/tcp

判读：本机 8080 端口已经被占了（要么另一个容器，要么一个直接跑在系统上的 nginx）。
下一步：二选一 —— 把新服务换到别的端口（-p 8081:80），或者把占用的那位停掉（docker stop old-nginx / systemctl stop nginx）。先确认那个服务是不是别人正在用的，再动手停。

三条链合起来：一张排查顺序图

容器没起来
 ├─ ① docker compose logs 服务名   → 有报错：按报错改（配置/依赖/参数）
 ├─ ② docker ps -a 看 Exited (N)   → 137/OOMKilled：内存问题
 │                                  143：被谁停了
 │                                  1：应用内部报错，回 ①
 └─ ③ 容器 Up 但连不上             → ss -tulnp 看端口 → 被占就换端口或停掉占用者

完成判定

□ 能不看笔记走完三条排查链　□ 能说出 137 和 143 各代表什么　□ 能故意造一个"端口被占"并解决掉　□ 能说出"容器 Up 但连不上"时第一步敲什么（ss -tulnp）

实验闭环：先记录原状态 → 操作 → 按输出 / 退出码验证 → 恢复现场。

回滚方式：练习造的故障容器全部 docker rm -f 清掉；改动过的端口配置改回原样。

踩坑记录位：现象 → 原因 → 解决 → 一句话总结（留空自己填）

实战价值：实战里最看重的就是"面对没见过的故障看推理路径"——容器故障的三条链是你手里最标准的一段推理。

业务场景

你阶段 2 写的三个脚本（backup / disk_alert / service_guard）现在只躺在你的机器上。同事说："换台机器就得重配一遍环境，能不能打包成镜像，谁拿去都能跑？"

□ 三个镜像都能 build 成功，且 docker history 里没有"又大又不该留"的层　□ 改阈值用 -e 传进去能触发告警　□ compose 两个服务都是 Up　□ 报告文件在宿主机目录里能找到　□ 陌生人照 README 能跑通（写法见 16 册《一个合格的 README 长什么样》）　□ 每一条都能说清"为什么这么做"

时间

3 小时（休息日）

产出

仓库 docker-scripts（或并进 shell-scripts 的 docker/ 目录）：三个 Dockerfile ＋ compose 文件 ＋ README ＋ 一张运行截图。

AI 运维指向

这是"把运维脚本变成可分发工具"的标准动作 —— 以后你把推理服务打成镜像、在 K8s 里跑，用的是同一套思路。

实战价值

别人问"你 Docker 到什么程度"，你可以说："我把自己写的三个运维脚本容器化了，参数用环境变量传，用 compose 管两个容器，结果落盘；镜像我做过瘦身，知道分层和缓存怎么影响构建速度。" —— 这段话说出来，Docker 这一项就过了。
